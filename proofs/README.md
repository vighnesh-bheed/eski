# Formal verification projects

The first phase groups correctness work for areas 1–6 and 9. Each project pairs an executable Lean model with mathematical specifications, kernel-checked theorems, an axiom audit and comparisons against actual Odin code. The individual project documentation defines the covered contracts, assumptions and remaining obligations.

| Group | Areas | Project |
| --- | --- | --- |
| Storage | 1. Hash-table resizing; 6. Memory accounting | [Storage](storage/README.md) |
| Command state | 2. Worker rollback; 3. Expiry and persistence | [Effects](effects/README.md) |
| Encoding | 4. Request parsing; 5. Packed data codecs | [Encoding](encoding/README.md) |
| Arithmetic | 9. Bit and integer operations | [Bitfields](bitfield/README.md) |

Areas 7 and 8, worker scheduling and fork/shutdown, have separate [bounded concurrency and lifecycle checks](../verification/README.md). Area 10 covers performance analysis and measurement; benchmarks remain deferred.

The vector packages have their own project, [Vectors](vector/README.md), which the aggregate runner includes after the first phase. It covers the Hadamard projection, int8 quantisation, binary encoding, scores and the arena free list in `src/vmath`, the candidate heaps, the visited set, the graph links, the link encoding and the twin chains in `src/hnsw`, compiled filter programs in `src/vfilter`, and the labelled vector set of `src/vsettype`: the exact merge of partition results, name resolution and the reader's view, the independence of each label's partition from what the reader cannot see, the agreement of the labels-off and labelled paths on a plain set, the move of an element between labels and the labelled vector set commands as the server dispatches them. Its receipt names its areas instead of numbering them.

The access labels have their own project, [Labels](label/README.md), which the aggregate runner includes after the vector project. It covers the label lattice with its trust ordering, the marking parser and formatter, the label table and its persistence encoding, the visibility bitsets, the accept adapters with a transcription of the filtered search of `src/hnsw`, the read and write rules and the label-partitioned counters in `src/label`, and in its `owners` area the owner order of `src/owner` and the arrival of a command's owner, with the key areas carried to principals of a label and an owner and a `forget` area for `OWNERS FORGET`. Its receipt also names its areas.

The retrieval leaves have three projects, which the aggregate runner includes after the label project. [Postings](postings/README.md) covers the Stream VByte codec, the sorted-array kernels, the Roaring bitmaps and their serialization, the cursor algebra and phrase windows of `src/postings` and `src/retrieve`, the label-partitioned term statistics and the BM25STD and RRF formulas. [Text](text/README.md) covers the byte classes, the document tokenizer, the Unicode 17.0.0 lower-casing and fold, the stop-word tables and the analysis position and stem rules in `src/text`. [Query](query/README.md) covers a fragment of the `src/ftquery` lexer and parser in dialects 1 and 2 and compares it with recorded reference output. Their receipts name their areas. `src/prefix` is not yet modelled.

## Run the proof projects

Use the pinned Lean 4.35.0 toolchain, Odin and Python 3.11 or newer. The [bitfield instructions](bitfield/README.md#run) describe obtaining the official compiler without a global installation. The effects project also needs the existing release Lua and diagnostics native archives prepared by the [normal dependency build](../docs/build-run-test.md#build); its verifier reads those inputs without rebuilding them. These projects use Lean core and Std; they do not add a server build or runtime dependency.

From the repository root:

```sh
LEAN_BIN_DIR=/absolute/path/lean-4.35.0-linux/bin python3 -I proofs/verify.py --odin /absolute/path/odin
```

The aggregate runner verifies projects sequentially: `storage`, `effects`, `encoding`, `bitfield`, `vector`, `label`, `postings`, `text` and then `query`. The text project reads the pinned Unicode 17.0.0 `UnicodeData.txt` and `SpecialCasing.txt` from `third_party/unicode/ucd-17.0.0`, as its [instructions](text/README.md) describe. `--odin` puts the named compiler first on the `PATH` every project uses and is passed to the vector, label, postings, text and query verifiers, which otherwise find Odin through `ODIN`, `PATH` or `~/odin/current/odin`. Use `--clean` for a fresh rebuild, `--project storage` or `--project bitfield vector` to select projects, `--list` to show the grouping and `--output /absolute/path` to select an artifact directory. Default artifacts remain under ignored `proofs/.build/phase-one/`, with a separate project log and receipt plus an aggregate receipt. The aggregate receipt is produced only after every selected project succeeds and its theorem assumptions, source fingerprints, per-area evidence and executable identities pass validation. The first-phase projects report numbered items and need comparison rows in every area. The vector project reports the named areas `projection`, `quantisation`, `heaps`, `visited`, `graph`, `arena`, `filter`, `merge`, `resolution`, `independence` and `compatibility`; `filter` is proof only and must report zero comparison rows, and every other area must report some. The label project reports the named areas `lattice`, `marking`, `interning`, `persistence`, `visibility`, `admission`, `rules`, `counters`, `contexts`, `arrival`, `owners`, `resolution`, `confinement`, `placement`, `purge`, `plain` and `forget`, and every one must report comparison rows. The postings project reports `svbyte`, `sorted`, `roaring`, `cursors`, `phrases`, `statistics` and `scoring`, the text project `classes`, `tokenizer`, `folding`, `stopwords` and `analysis`, and the query project `lexer`, `parser` and `reference`; every one must report comparison rows. The aggregate receipt lists the numbered items under `items` and the named areas under `areas`.

The proofs establish that the Hadamard rows are orthogonal exactly when the row count is at most the largest power of two dividing the input dimension, so accepted non-power-of-two inputs can give non-orthogonal rows; that the int8 quantiser reconstructs within `range / 254` whenever its scale is finite, and stores all-zero codes, so a reconstruction error up to `range`, when `127 / range` overflows f32 as it does for every subnormal-only input; that the binary Hamming bound and the score range rest on the padding condition that `bin_padding_clear` checks exactly; that a live arena norm never has bit 31 set, so a free entry is never mistaken for a live slot, that `arena_free` rejects double frees and invalid slots, and that the free list is acyclic and ends at its terminator; that the heaps keep their order and return the extreme candidate; that the one-byte visited stamps report exactly the slots marked since the last begin, with the stamp array cleared every 255 searches; that insertion, eviction with adoption, removal and repair keep links two-way, duplicate free, within `M` and `2M` and free of self links and of the removed node, that no eviction leaves its victim without a link, and that searching every layer before linking builds the same graph; that re-encoding the links at a wider width leaves the adjacency unchanged; that the twin chains are acyclic, start at their head node, end at `NONE`, keep `next(prev(t)) = t`, the twin and live counts and a node entry at the top level, and that insert, remove and the attach, detach and promote steps keep these invariants together with graph well-formedness; and that a compiled filter reading a missing field evaluates to false while constant folding agrees with run-time evaluation. For the labelled vector set, the proofs establish that merging each visible partition's own top COUNT by score and then name gives the top COUNT of their union, with FILTER inside each partition, EPSILON after the merge, TRUTH as a brute force, and graph partitions contributing exactly their own results. They establish that name resolution picks the copy at the command's label, otherwise the highest visible copy by level, then compartment count, then trust, then age, and depends only on the visible copies. The view object, every resolved copy and every range depend only on the visible part of the set. A command at a label the reader cannot see never changes that visible part, and after any history it equals the visible part after the history with those commands removed, so a partition's state and its label's stream depend only on commands at labels the partition's label dominates. A pinned partition never changes mode, and conversion keeps its footprint. On a set that was never converted, labelled writes at BOTTOM are the labels-off writes and the labelled reads give the labels-off answers, with the same sequence of scores in search. The [project documentation](vector/README.md) states the models, assumptions and the cases outside the proofs. An element move between labels is a removal at the source followed by a raw insert at the target, with the contents unchanged, the moved copy the youngest of its name and nothing visible to a reader who sees neither label. At command level, every vector-set command's reply is unchanged when the state is restricted to the command's label, the resolved key copy depends only on visible copies, purging every command an observer cannot see leaves the observer's replies unchanged, and a single-level scheme leaves labels off. With owner scopes, a reader at a label and an owner sees shared data and its own data at the labels its label dominates and nothing of another owner. Resolution takes the reader's own copy at its exact label, then the shared copy at that label, then the highest visible rank, an own copy before a shared one of equal rank and then the oldest copy within a scope, whatever the interleaving of copies of different scopes, and INUSE names that copy. A user with no copies of its own, including one just forgotten, reads every name, view and range exactly as a shared reader at the same label. The names left unshadowed in a view are unique in every reachable state, so the merge over own and shared partitions is exact and independent of the partition order. Another owner's commands at any label, and its FORGET, never change a reader's visible state, and one stream per scope keeps other owners' draws from shifting a reader's draws. Graduating or flattening a compact owner block changes only that owner's accounting, and with every copy and command at one owner, SHARED or a user, the owner model is the labels model.

## Query parser

The query project contains 54 named contract theorems and 231 kernel-checked theorems. Its comparison rows run the Lean model and the actual imported `ftquery` lexer, parser and EXPLAIN printer on one deterministic case file and check both against independent Python expectations and, for recorded cases, against the reference output recorded in the package's test data.

## Audit coverage

The shared [audit runner](kernel_audit.py) uses [Lean's loaded environment](KernelAudit.lean) to inspect declarations by their source module. It recursively builds and imports every project Lean module, including `Main`, and checks the dependency closure of every project-origin declaration against `propext`, `Classical.choice` and `Quot.sound`. Project axioms, admitted proofs and native-evaluation proof axioms are rejected, including declarations outside the usual namespace or absent from the printed contract manifest. Private and generated declarations are included. A module that cannot be inventoried stops verification.

The printed contract manifest names the mathematical results used in each area's evidence. Receipts distinguish those named theorems from the larger kernel theorem inventory, which also includes generated results. `kernel-inventory.json` records module, source, compiled-artifact and audit-tool identities; the aggregate runner checks that inventory and its agreement with the named manifest. Source text layout is not used to decide which declarations require dependency checks.

Formal proofs apply to the Lean definitions. Actual Odin comparisons provide finite evidence of correspondence. The project documents distinguish proved properties from tested behavior and do not establish a verified translation of the Odin executable. Memory accounting concerns charged, reserved or requested bytes, with the pool ledger, table bytes and key cells described by the storage project; it does not measure process RSS or bytes per stored key. Performance benefits require separate implementation changes and measurements.
