# Postings and ranking contracts

This optional Lean 4.35.0 project covers the retrieval leaves below the query engine: the Stream VByte codec in `src/svbyte`, the sorted-array kernels in `src/sorted`, the Roaring bitmaps and their portable serialization in `src/roaring`, the posting lists in `src/postings`, the cursor algebra and phrase windows in `src/retrieve`, the label-partitioned term statistics in `src/termstats` and the ranking formulas in `src/bm25std` and `src/rrf`. It uses only Lean core and adds no server dependency. The theorems are about Lean definitions that transcribe the Odin procedures; the bridge supplies finite evidence that the actual packages agree with them, and makes no claim that the Odin executable is formally verified.

Run from the repository root:

```sh
python3 -I proofs/postings/verify.py --lean-bin /absolute/path/to/lean/bin --odin /absolute/path/to/odin --output /absolute/path/to/results
```

`LEAN_BIN_DIR` supplies the Lean directory when `--lean-bin` is omitted, and the Odin compiler is taken from `--odin`, then `ODIN`, then `PATH`, then `~/odin/current/odin`. The default output directory is `proofs/postings/.build`. The verifier removes a previous success receipt, checks the source drift gate, builds the Lean library and `postings_model` executable and the Odin harness with `-vet -strict-style` under the repository's `.build/proofs/compiler.lock`, runs the shared [kernel audit](../README.md#audit-coverage) with `Postings.lean` as the printed manifest, generates the deterministic corpus, runs both executables on it and compares every row with independent Python expectations and with each other. It uses nice 10, one allowed CPU and one Lean thread and starts no server. The [aggregate runner](../README.md#run-the-proof-projects) runs it as `--project postings`.

`Postings/Svbyte.lean` proves the codec round trip and that decoding is canonical: every accepted encoding is the shortest one, with one control code per value. `Postings/Sorted.lean` proves each kernel equal to its set operation on strictly increasing inputs and the galloping search equal to the binary bounds. `Postings/Roaring.lean` proves the add, remove, membership, cardinality and the three set operations against plain sets, that iteration is strictly increasing, that run optimisation keeps the contents, and that deserialization inverts serialization and returns only well-formed bitmaps. Two model findings are recorded as theorems: `offsets_ignored` shows the decoder never reads the offset table, and `reencode_stable` shows that inputs with adjacent runs or padded flags, which the decoder accepts though the encoder never writes them, re-encode to a stable canonical form. `Postings/Cursor.lean` proves the drains produce exactly the set intersection, union and difference without repeating a document. `Postings/Phrase.lean` proves the ordered window exact, and the unordered sweep sound and complete only when the lists share no position: `unordered_counterexample` gives `[[5], [5, 6]]` with slop 0, which the sweep rejects although choosing 5 and 6 gives a window within the slop, because the sweep needs the largest head to exceed the smallest. `Postings/Stats.lean` proves the property P5 of the query contract: visible totals equal sums over visible label partitions and do not change when only hidden partitions change; `hidden_overflow_interference` shows the one exception: an addition to a visible partition is refused at the u64 ceiling of the shared total when hidden partitions hold the rest. `Postings/Score.lean` proves the BM25STD and RRF formula properties stated in the table.

The bridge [bridge.odin](bridge.odin) imports the nine packages directly and replays the same case file as [Main.lean](Main.lean); the independent Python model in [verify.py](verify.py) computes the expected rows with sets, sorting, `struct` and `math.log`. Floating-point rows are compared as IEEE-754 bit patterns; Lean `Float.log`, Odin `libc.log` and Python `math.log` all call the C library. The deterministic seed `0x9057195` gives 22,097 rows: 2,300 Stream VByte rows over 18,777 values, 2,700 sorted-kernel rows, 3,855 Roaring rows with 491 bitset and 194 run containers and 662 decodes, 409 accepted, 3,420 cursor and tree rows over 1,568 posting lists, 3,001 phrase rows, 2,120 statistics rows with 1,296 hidden-partition operations and 4,701 scoring rows. Every row kind and column is mutated as a negative control, together with empty, truncated and extra output and 23 semantic mutants, among them delta decoding without prefix sums, a decoder that over-reads, galloping that ignores its start, an intersection that keeps the left list, a union that drops the right list, a difference that keeps excluded documents, bitsets and runs never built, counted offsets, rejected trailing bytes, unsorted iteration, accepted out-of-order postings, collected deleted documents, INORDER ignoring order, an unordered window accepting equal positions, visible totals including hidden partitions, a BM25 with a parenthesised numerator, an idf without the maximum, an RRF ignoring its window and a reversed top-k. All 135 controls must be rejected. [source-sha256.json](source-sha256.json) pins the 24 modelled sources; a change stops verification for review and reconciliation. Hashes detect drift; they do not establish refinement.

The receipt records the named theorem manifest with each theorem's axioms, the kernel inventory, per-area theorem names and comparison counts, source, trace, result and executable hashes and the compiler versions. The areas are `svbyte`, `sorted`, `roaring`, `cursors`, `phrases`, `statistics` and `scoring`, and each has comparison rows. All 286 named theorems and all 1,400 kernel-checked theorems depend only on `propext`, `Classical.choice` and `Quot.sound`; there is no `sorry`, no project axiom and no native evaluation. The posting block codec and its flush and load paths, the block-skipping intersection strategy, the SIMD kernels, the writer, the document table, the tag and numeric indexes, the remove-and-collect sequence of the integration notes and floating-point rounding beyond bit-for-bit comparison are outside the proofs. No performance claim is made here.
