# Storage contracts

This optional Lean 4.35.0 project covers selected contracts from phase-one area 1, main-keyspace table resizing and lookup, and area 6, memory accounting for the requested-byte pool, the key table and timed key cells. Both partition roles are covered: ordinary partitions, which keep key cells in the slab and tables in mappings, and the heap role of owner partitions, which never uses the slab, keeps its key cells in the heap forms and holds tables of up to 1,024 slots in plain heap blocks. It uses only Lean core/Std. It adds no server dependency and makes no claim that the Odin executable is formally verified.

Run from the repository root with an official Lean 4.35.0 toolchain:

```sh
python3 proofs/storage/verify.py --lean-bin /absolute/path/to/lean/bin --output /absolute/path/to/results
```

`LEAN_BIN_DIR` supplies the toolchain directory when `--lean-bin` is omitted. The default output directory is `proofs/storage/.build`. The verifier builds the Lean model and a focused actual-Odin bridge, checks the named contract manifest and every project-origin kernel declaration against the allowlist `propext`, `Classical.choice`, `Quot.sound`, and compares both executables against independently computed Python expectations. It clears a previous success receipt before checking source hashes or building. Builds share the repository's `.build/proofs/compiler.lock`, run at nice 10 on one allowed CPU, use one Lean thread and two Odin compiler threads, and start no workers or server.

`Storage/Table.lean` is an executable scalar model. An entry holds an abstract key identifier, its hash, the 64-bit value-handle bits, the 16-bit access stamp and a key cell with the key length, the timed flag of the key handle and the deadline. Slot contents are the stamp and the two handles, 18 bytes; the deadline is not part of a slot. The home group is `floor(hash * groups / 2^64)`. The probe walk follows `table_alloc` and `probe_next`: the span is the smallest power of two at least the group count, each step adds the step number and masks with span minus one, and positions at or past the group count are skipped. The walk is bounded to one span of steps; the Odin loop is unbounded and stops at a group holding an empty control, so the model's `none` corresponds to a case the server cannot reach while a table keeps an empty slot. Capacities are any multiple of 16. Growth is `max(cap + 16, ceil16(cap * 3 / 2))` and shrink rounding is `max(16, ceil16(n))`. The rehash loop is a bounded recursion over the source groups with the actual budget, partial-group and swap rules.

`Storage/Probe.lean` proves the span is a power of two covering the group count, that the masked recurrence equals the closed form `(home + k(k+1)/2) mod span` filtered to real groups, that triangular numbers reach every residue modulo a power of two (the reflection `k -> 2^(m+1) - 1 - k` shifts a residue by `2^m`), and therefore that the probe from any home reaches every group and a claim succeeds whenever any slot is free.

`Storage/Placement.lean` states the placement invariant: every live slot lies in a group on the probe path of its own hash, and every earlier group on that path holds no empty control. Claims, in-place updates that keep the hash, tombstones and erases preserve it; an erase may write an empty control only into a group that already had one, which can never be an earlier group of any path. The invariant gives lookups that find every present key, exactly its slot under unique keys. A second invariant says every source group below the migration cursor holds no live slot; with live-counter consistency it proves that the whole rehash, including the final swap, preserves any additive measure of the entries, so keys are still present and found after the rehash in either direction. Bank-level insertion and deletion keep both invariants and change the measures by exactly the inserted, updated or removed entry.

`Storage/Scan.lean` models `scan_round`: without a migration it takes one home group of the table and returns `group_floor`, the smallest hash with the next home; during a migration it takes the home of the narrower table and every home of the wider table whose hash range meets the same cursor interval. `group_floor` and the home function form an exact threshold pair. Each round returns every key placed in a scanned bank whose hash lies between the cursor and the returned threshold, and the threshold strictly increases until it wraps to zero. Over any sequence of states, so with arbitrary insertions, deletions, migration batches and resizes between rounds, a completed iteration returns every key present at each of its rounds. Keys may be returned more than once. Pattern matching, expired-key filtering, the COUNT loop of `db_scan` and the recomputed key hash (the model uses the stored hash) are outside the proof.

`Storage/Cells.lean` names the partition role, `slab` for ordinary partitions and `heap` for the heap role (`DB_ROLE_HEAP`, the only role bit the store tests), and defines everything role-dependent through three functions of the role: the key form, the table bytes and the mapped table bytes. A key cell's form is inline for an untimed key of at most seven bytes in either role; otherwise the slab role uses a slab cell while the cell (with the deadline for a timed key) fits in 4,096 bytes and the heap form beyond that, and the heap role always uses the heap form. The layout cost of a form is zero inline, the key length plus eight deadline bytes when timed in the slab, and the key length plus an eight-byte length word plus the deadline when timed in the heap; `keyBytes` is the slab role's cost by definition, so the earlier labels-off model is unchanged. Mapped table bytes are the page-rounded sum of the 64-byte-rounded control bytes and 18 bytes per slot; a heap table, used by the heap role while the capacity is at most 1,024 slots, is the same sum without the page rounding, and only mapped tables count as mapped bytes. A keyspace carries its role and pairs the banks with a timed-key counter, a key-cell byte counter, a table byte counter and a mapped byte counter maintained the way `key_set_deadline`, `db_upsert_in`, `db_erase`, `table_alloc_for`, `table_alloc`, `table_alloc_heap` and `table_detach` maintain theirs. The soundness invariant bundles exact counters, placement, live-counter consistency, the cursor invariant, capacities that are multiples of 16 and an empty destination while idle; reset, insertion or update, deletion, resize start, migration, the production resize start and `db_make_room` preserve it for either role, and under it every present key is found. The soundness proofs use the role only through the per-entry key cost and the per-bank table costs, both zero for an empty bank, so another representation can be added as a further role by giving its key forms and table costs and re-proving only those formula theorems. The production resize start is modeled as a resize start followed, when the source has at most `REHASH_SYNC_CAP` slots, by one migration with the unbounded budget that `db_rehash_finish` passes; the Odin loop repeats that call until the migration ends, which a single call already achieves whenever the destination has room, and the model leaves a migration that cannot finish unchanged where the server would not return. `db_make_room` is modeled without its first-table branch for a partition that holds no table and without the maxmemory step to `table_tight_cap`.

Key/value handles are abstract identifiers in the proofs, and the model's lookup matches by key identifier and hash, independently of the key's form. The bridge uses seven-byte and twelve-byte keys under the role bits 0, 2, 4 and 12, so it exercises inline, slab and heap key cells, timed and untimed, and both table kinds; heap-form keys of more than 4,096 bytes in the slab role, the slab size classes of key cells and the prepared-next table window are modeled or bounded only by the formulas above and are not exercised by the bridge. String values are outside the Lean model; the bridge's value comparison covers the heap role's value path only, including empty values and the empty-data block that `entry_heap_close` builds from an empty buffer, which the value mode reaches through `entry_setrange` with an empty patch although no command makes that call, and it has no Lean counterpart. Hash consistency between a stored entry and its key bytes, slab and heap allocation success, object interpretation, SIMD refinement, pointer safety, virtual-memory success, prefetch behavior, compiler correctness and the full `db_upsert_in`, `db_make_room`, including its `table_tight_cap` five-fourths step when the three-halves table would exceed maxmemory, and `db_prepare_next` effects remain outside the proof. Datatype-specific hash/set/sorted-set/stream tables are separate algorithms and are outside this project.

`Storage/Ledger.lean` models the requested-byte pool ledger as an operational `used` counter plus independently maintained owned tokens. `Valid` asserts equality with the outstanding-token sum, nonnegative charges, unique token IDs and a signed 64-bit budget. Reserve updates the counter and adds a fresh token; release searches/removes a token and subtracts its charge. Acquire validates positive payload and the 32-byte header bound, reserves, then explicitly releases the reservation if the modeled heap attempt fails. The inverse theorem proves that rollback restores the ledger. Successful admission is proved safe under nonnegative existing balances and budgets at most `2^63-1`; zero-byte external reservations succeed within budget and preserve the numeric balance. Requested bytes include the allocation header and are not RSS, libc usable-size, mapped pages or OS memory pressure.

Fresh IDs and one consumption per token are ghost ownership obligations on callers. The actual external reserve/release API does not track IDs or reject double release; raw release requires the caller to own exactly that outstanding charge. The formal model's missing-token rejection is an ownership guard, not a runtime guarantee. Wrong-pool and wrong-length free tests use still-live allocations that the real `free` API safely rejects; no raw double free or unowned positive external release is attempted. Actual heap-allocation failure is not fault-injected; its arithmetic rollback is modeled/proved, while a real compound record/seed admission failure exercises production rollback. The allocator wrapper's resize/copy semantics and snapshot/object charge estimation or alias correctness are not proved by this project; their source fingerprints require review after drift. Worker concurrency, CAS linearizability, mutable limits during allocation, reference-count races and all scheduling/lifecycle properties remain separate work.

The deterministic corpus contains 20,404 table-operation comparisons, 3,639 SCAN-round comparisons and 1,527 accounting-operation comparisons, 25,570 rows that both executables must reproduce, plus 1,174 value-path rows that only the bridge reproduces. The labels-off part is the earlier corpus with unchanged operations and seeds; a second seed adds the role scenarios, and a fixed scenario under role bits 0, 12 and 4 stores, finds, deletes, rewrites and re-times short and long keys with deadlines. It covers 327 resizes (73 by the production growth rule, 75 by the production shrink rule, 36 production resize starts and 58 `db_make_room` calls, 84 of these finishing synchronously, and the rest with explicit capacities; the growth rule calls `table_grow_cap` when the live count exceeds seven sixteenths of the capacity, as `db_make_room` does while the larger table fits under maxmemory, and the shrink rule calls `table_round_cap` on twice the live count, as `db_shrink` does), 339 tables whose group count is not a power of two, capacities from 16 to 4,096 slots, 4,980 heap-role table operations on 101 heap tables and 13 mapped tables, 8 heap-role resizes from a heap table to a mapped table and 7 back, 1,172 partial batches, 155 zero-budget batches, repeated migration, final swaps, updates/deletions between batches, 120 keys sharing the last home group and low-seven-bit hash tag in three-, four- and five-group tables, 875 twelve-byte insertions, 784 heap-form key insertions, 170 untimed slab-key insertions, 342 lookups that find a timed key of at most seven bytes in a heap-role partition, 8,748 queries, 2,503 deletions, 1,324 timed insertions, 329 deadlines set on untimed keys, 220 cleared and 168 updated in place, value/deadline/stamp extrema, 607 complete SCAN iterations whose 17,977 key presences are checked by the oracle, small and signed-64-bit admission boundaries, 24 safe rejected ownership/length checks and 12 real record-seed rollbacks. The value-path rows cover 662 stores, 128 appends, 112 range writes, 40 slab-to-heap moves and 232 erasures under role bits 12 and 4, with 166 empty writes, 374 empty results of which 114 are heap values, 18 rows holding an empty-data block, 6 stores onto one and 354 heap-block reallocations, over lengths from zero to 5,000 bytes. Python uses a separate key-to-entry dictionary, the closed-form triangular offset for placement and probing, the per-role key-cell cost written as one closed formula rather than through the key form, and counters recomputed from occupied/deleted slots and timed entries. It validates the physical inventory against the dictionary after every table operation and checks that every table keeps its reserve of empty slots. Its fixed-seed hash oracle for keys of four to sixteen bytes uses wide-integer arithmetic, and every insertion/query/deletion checks that the supplied hash equals the actual Odin hash. Its value oracle tracks each value's form, bytes and block capacity and recomputes the heap counters. Finite agreement remains tested evidence, not a proof of Odin equivalence.

The bridge copies `src/table.odin` and `src/hash.odin` byte-for-byte into a private output overlay, copies the value-type prefix of `src/value.odin`, and appends exact slices of the constants `DB_ROLE_HEAP`, `DB_ROLE_OWNER`, `REHASH_SYNC_CAP`, `ENTRY_RING`, `BIG_STR_BYTES` and `STRING_DOUBLING_LIMIT`, the `Entry` type and the procedures `mem_alloc`, `mem_free`, `key_store`, `key_store_heap`, `key_store_timed`, `key_store_timed_heap`, `key_release`, `key_restore`, `key_set_deadline`, `db_locate`, `db_erase`, `db_rehash_swap`, `db_rehash_groups`, `db_rehash_finish`, `db_rehash_start`, `table_alloc_for`, `db_rehash_begin`, `db_drop_next`, `db_make_room`, `scan_take_home`, `scan_round`, `big_new`, `big_attach`, `val_release`, `entry_load`, `entry_view`, `entry_store`, `entry_store_heap`, `entry_append`, `entry_append_heap`, `entry_heap_open`, `entry_heap_close`, `string_grown_capacity`, `entry_setrange` and `db_move_heap` from `src/store.odin`, and of `SLAB_UNIT`, `SLAB_MAX`, `SLAB_CLASSES`, `slab_class_size`, `slab_class` and `slab_size_of` from `src/slab.odin`. Each slice's source and hash are recorded. It directly imports the keyspace package. The harness supplies a reduced database context with the production role byte, a bump slab that records requested bytes, a fatal handler, an immediate unmap callback that also lowers the mapped-table counter as `storage_unmap` does, object-release and memcached-metadata stubs that stop the run if they meet objects or metadata, no maxmemory limit, and a scan pass that prints offered keys. Every resize allocates its destination through `table_alloc_for`. Each table header reports whether the table is a heap block (`warm_at` below zero, the mark `table_detach` and `lazyfree_run` test) or a mapping, and each slot reports its key form. It asserts that a timed key's deadline occupies the eight bytes in front of its slab key bytes or in front of its heap key's length word, that a heap key's length word matches its bytes, that the global used-memory counter equals the partition's heap bytes, and that releasing every key between scenarios returns the slab, heap, table, mapped and rehash counters to zero. The value mode writes a string value into one slot through the actual value procedures, or moves one into an empty slot through `db_move_heap` with the two assignments `db_move` makes after it, and prints the value form, length, capacity, heap counters, slab bytes, whether a heap block has no data, and a checksum of the bytes. A source drift gate covers every imported keyspace source plus the mapped main-keyspace/accounting files. Hashes detect drift and identify artifacts; they do not establish refinement.

The receipt records the complete theorem/axiom manifest, per-area theorem names and comparison counts, source/model/trace/result hashes, exact compiler versions and tool/executable hashes, and the overlay slice identities. Controlled empty/truncated/extra output, every table output column including the role column, each of the four counters, the role value, the table kind and the key form of a heap-role row, the destination kind of a heap-to-mapped resize, the key form of an untimed slab key, the SCAN key and cursor columns, both accounting columns, every value-path column, a truncated value output, the empty-data flag, the earlier 16-byte charge of an empty heap value and the earlier matcher's miss on a short timed heap key must be rejected as mutants. Missing tools, empty evidence, output noise, drift or failed comparisons produce no success receipt. No benchmark or performance claim is made.
