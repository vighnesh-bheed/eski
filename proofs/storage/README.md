# Storage contracts

This optional Lean 4.35.0 project covers selected contracts from phase-one area 1, main-keyspace table resizing and lookup, and area 6, memory accounting for the requested-byte pool, the key table and timed key cells. Both partition roles are covered: ordinary partitions, which keep key cells in the slab and tables in mappings, and the heap role of owner partitions, which never uses the slab, keeps its key cells in the heap forms and holds tables of up to 1,024 slots in plain heap blocks. In the compact owner form the smallest table is a short table of 1, 2 or 4 lanes behind one 16-byte control group, which grows through a ladder to the full 16-slot heap table and is compacted back to 4 lanes when only its first two lanes hold keys; owner tables above 1,024 slots are mappings marked never-warm. It uses only Lean core/Std. It adds no server dependency and makes no claim that the Odin executable is formally verified.

Run from the repository root with an official Lean 4.35.0 toolchain:

```sh
python3 proofs/storage/verify.py --lean-bin /absolute/path/to/lean/bin --output /absolute/path/to/results
```

`LEAN_BIN_DIR` supplies the toolchain directory when `--lean-bin` is omitted. The default output directory is `proofs/storage/.build`. The verifier builds the Lean model and a focused actual-Odin bridge, checks the named contract manifest and every project-origin kernel declaration against the allowlist `propext`, `Classical.choice`, `Quot.sound`, and compares both executables against independently computed Python expectations. It clears a previous success receipt before checking source hashes or building. Builds share the repository's `.build/proofs/compiler.lock`, run at nice 10 on one allowed CPU, use one Lean thread and two Odin compiler threads, and start no workers or server.

`Storage/Table.lean` is an executable scalar model. An entry holds an abstract key identifier, its hash, the 64-bit value-handle bits, the 16-bit access stamp and a key cell with the key length, the timed flag of the key handle and the deadline. Slot contents are the stamp and the two handles, 18 bytes; the deadline is not part of a slot. The home group is `floor(hash * groups / 2^64)`. The probe walk follows `table_alloc` and `probe_next`: the span is the smallest power of two at least the group count, each step adds the step number and masks with span minus one, and positions at or past the group count are skipped. The walk is bounded to one span of steps; the Odin loop is unbounded and stops at a group holding an empty control, so the model's `none` corresponds to a case the server cannot reach while a table keeps an empty slot. Capacities are any multiple of 16. Growth is `max(cap + 16, ceil16(cap * 3 / 2))` and shrink rounding is `max(16, ceil16(n))`. The rehash loop is a bounded recursion over the source groups with the actual budget, partial-group and swap rules.

`Storage/Probe.lean` proves the span is a power of two covering the group count, that the masked recurrence equals the closed form `(home + k(k+1)/2) mod span` filtered to real groups, that triangular numbers reach every residue modulo a power of two (the reflection `k -> 2^(m+1) - 1 - k` shifts a residue by `2^m`), and therefore that the probe from any home reaches every group and a claim succeeds whenever any slot is free.

`Storage/Placement.lean` states the placement invariant: every live slot lies in a group on the probe path of its own hash, and every earlier group on that path holds no empty control. Claims, in-place updates that keep the hash, tombstones and erases preserve it; an erase may write an empty control only into a group that already had one, which can never be an earlier group of any path. The invariant gives lookups that find every present key, exactly its slot under unique keys. A second invariant says every source group below the migration cursor holds no live slot; with live-counter consistency it proves that the whole rehash, including the final swap, preserves any additive measure of the entries, so keys are still present and found after the rehash in either direction. Bank-level insertion and deletion keep both invariants and change the measures by exactly the inserted, updated or removed entry.

`Storage/Scan.lean` models `scan_round`: without a migration it takes one home group of the table and returns `group_floor`, the smallest hash with the next home; during a migration it takes the home of the narrower table and every home of the wider table whose hash range meets the same cursor interval. `group_floor` and the home function form an exact threshold pair. Each round returns every key placed in a scanned bank whose hash lies between the cursor and the returned threshold, and the threshold strictly increases until it wraps to zero. Over any sequence of states, so with arbitrary insertions, deletions, migration batches and resizes between rounds, a completed iteration returns every key present at each of its rounds. Keys may be returned more than once. Pattern matching, expired-key filtering, the COUNT loop of `db_scan` and the recomputed key hash (the model uses the stored hash) are outside the proof.

`Storage/Lanes.lean` gives a table its lane count, which is the capacity for every table except a short one. A short table is modeled as what every procedure sees, one group of 16 slots, whose memory holds only the first `lanes` slots. Its lane bound says every non-empty slot lies below the lane count, no slot is a tombstone and live plus growth plus tombstones equals the lane count; the bound makes every slot access stay inside the allocation. In a one-group table the claim takes the lowest free slot, and the proofs show that a claim made while growth is positive lands below the lane count and keeps the bound, that an erase writes an empty control (lanes below 16 always leave one) and keeps it, and that a fresh short table satisfies it. Migrating a one-group source whose live slots are exactly the first `n` lanes into an empty one-group destination puts every entry at its own index, so the whole bounded rehash with its swap returns a table whose slots equal the source's slot for slot; this is what makes a ladder step invisible to lookups, SCAN and random sampling. Compaction copies the first two lanes into a zeroed 4-lane short table; when no live slot lies at or above lane 2 it keeps every live slot at its index, every additive measure of the entries, placement, the live counter, and (given no tombstone cells) the lane bound. Lane counts travel with their tables through upsert, removal, migration and swap.

`Storage/Cells.lean` names the partition role, `slab` for ordinary partitions and `heap` for the heap role (`DB_ROLE_HEAP`, the only role bit the store tests), and defines everything role-dependent through three functions of the role: the key form, the table bytes and the mapped table bytes. A key cell's form is inline for an untimed key of at most seven bytes in either role; otherwise the slab role uses a slab cell while the cell (with the deadline for a timed key) fits in 4,096 bytes and the heap form beyond that, and the heap role always uses the heap form. The layout cost of a form is zero inline, the key length plus eight deadline bytes when timed in the slab, and the key length plus an eight-byte length word plus the deadline when timed in the heap; `keyBytes` is the slab role's cost by definition, so the earlier labels-off model is unchanged. Mapped table bytes are the page-rounded sum of the 64-byte-rounded control bytes and 18 bytes per slot; a heap table, used by the heap role while the capacity is at most 1,024 slots, is the same sum without the page rounding, and only mapped tables count as mapped bytes. A short table of `K` lanes costs `16 + 18·K` bytes and no mapped bytes, so 34, 52 and 88 bytes for 1, 2 and 4 lanes against 352 for the full 16-slot heap table; the bytes of a table depend only on its lane count and slot count. Allocation follows `table_alloc_for` and `table_alloc_owner`: the slab role always takes `table_alloc`; the heap role with `owner_compact` takes, at 16 slots, 1 lane when the partition holds no table and twice the current table's lanes otherwise, as long as that is below 8, and the full 16-slot heap table from there; any other capacity up to 1,024 slots is a heap table and anything larger a mapping. A keyspace carries its role and the compact flag and pairs the banks with a timed-key counter, a key-cell byte counter, a table byte counter and a mapped byte counter maintained the way `key_set_deadline`, `db_upsert_in`, `db_erase`, `table_alloc_for`, `table_alloc_owner`, `table_alloc`, `table_alloc_heap`, `table_alloc_short`, `db_table_compact` and `table_detach` maintain theirs. An insertion follows `db_upsert_in`: when the key is absent, the target table has no growth left and the chosen slot is empty, `db_make_room` runs first. The soundness invariant bundles exact counters, placement, live-counter consistency, the cursor invariant, capacities that are multiples of 16, an empty destination while idle and table shapes in which only the heap role holds short tables; reset, insertion or update by either rule, deletion, resize start, migration, the production resize start, `db_make_room` and compaction preserve it for either role, and under it every present key is found. Across a ladder step started by `db_make_room` from a table whose live slots are exactly its first lanes, every slot keeps its entry; compaction lowers the table counter by exactly 264 bytes and leaves the mapped counter alone. The lane bound is proved per operation (claim with growth, erase, fresh allocation, compaction, ladder migration) and not threaded through the keyspace invariant; the bridge checks it on every row. The soundness proofs use the role only through the per-entry key cost and the per-bank table costs, both zero for an empty bank, so another representation can be added as a further role by giving its key forms and table costs and re-proving only those formula theorems. The production resize start is modeled as a resize start followed, when the source has at most `REHASH_SYNC_CAP` slots, by one migration with the unbounded budget that `db_rehash_finish` passes; the Odin loop repeats that call until the migration ends, which a single call already achieves whenever the destination has room, and the model leaves a migration that cannot finish unchanged where the server would not return. `db_make_room` is modeled without its first-table branch for a partition that holds no table and without the maxmemory step to `table_tight_cap`.

Key/value handles are abstract identifiers in the proofs, and the model's lookup matches by key identifier and hash, independently of the key's form. The bridge uses seven-byte and twelve-byte keys under the role bits 0, 2, 4 and 12, so it exercises inline, slab and heap key cells, timed and untimed, all three table kinds and short tables of every ladder size; heap-form keys of more than 4,096 bytes in the slab role, the slab size classes of key cells and the prepared-next table window are modeled or bounded only by the formulas above and are not exercised by the bridge. String values are outside the Lean model; the bridge's value comparison covers the heap role's value path only, including empty values and the empty-data block that `entry_heap_close` builds from an empty buffer, which the value mode reaches through `entry_setrange` with an empty patch although no command makes that call, and it has no Lean counterpart. Hash consistency between a stored entry and its key bytes, slab and heap allocation success, object interpretation, SIMD refinement, pointer safety, virtual-memory success, prefetch behavior, compiler correctness and the full `db_upsert_in`, `db_make_room`, including its `table_tight_cap` five-fourths step when the three-halves table would exceed maxmemory, and `db_prepare_next` effects remain outside the proof. Datatype-specific hash/set/sorted-set/stream tables are separate algorithms and are outside this project.

`Storage/Ledger.lean` models the requested-byte pool ledger as an operational `used` counter plus independently maintained owned tokens. `Valid` asserts equality with the outstanding-token sum, nonnegative charges, unique token IDs and a signed 64-bit budget. Reserve updates the counter and adds a fresh token; release searches/removes a token and subtracts its charge. Acquire validates positive payload and the 32-byte header bound, reserves, then explicitly releases the reservation if the modeled heap attempt fails. The inverse theorem proves that rollback restores the ledger. Successful admission is proved safe under nonnegative existing balances and budgets at most `2^63-1`; zero-byte external reservations succeed within budget and preserve the numeric balance. Requested bytes include the allocation header and are not RSS, libc usable-size, mapped pages or OS memory pressure.

Fresh IDs and one consumption per token are ghost ownership obligations on callers. The actual external reserve/release API does not track IDs or reject double release; raw release requires the caller to own exactly that outstanding charge. The formal model's missing-token rejection is an ownership guard, not a runtime guarantee. Wrong-pool and wrong-length free tests use still-live allocations that the real `free` API safely rejects; no raw double free or unowned positive external release is attempted. Actual heap-allocation failure is not fault-injected; its arithmetic rollback is modeled/proved, while a real compound record/seed admission failure exercises production rollback. The allocator wrapper's resize/copy semantics and snapshot/object charge estimation or alias correctness are not proved by this project; their source fingerprints require review after drift. Worker concurrency, CAS linearizability, mutable limits during allocation, reference-count races and all scheduling/lifecycle properties remain separate work.

Python uses a separate key-to-entry dictionary, its own allocation and byte rules for short tables, a lane-bound check on every row, the closed-form triangular offset for placement and probing, the per-role key-cell cost written as one closed formula rather than through the key form, and counters recomputed from occupied/deleted slots and timed entries. Each table header reports its lane count (`len(t.slots)`) and whether the table is a heap block (`warm_at == TABLE_HEAP_WARM`, the mark `table_detach` and `lazyfree_run` test), a never-warm owner mapping (`TABLE_COLD_WARM`) or an ordinary mapping, and each slot reports its key form; the bridge asserts that no control byte at or above the lane count is ever non-empty and that heap blocks are 64-byte aligned (16 for short tables).
