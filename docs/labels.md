# Labels

Labels let one Eski node hold data for readers with different clearances. A label is a level, a set of compartments and a trust level. The operator configures the scheme of names, each login gets a clearance, and every command runs at one label that the application asserts for it. This release builds who is asking (the scheme, the logins, the ways a label arrives with a command, contexts, signed levels, transactions and scripts, labelled pub/sub, the server-wide channels, the audit file and snapshots that keep every label) and what is stored: every key of the ordinary types carries the label of the command that created it, and every vector set element carries the label of the command that wrote it.

Without a scheme Eski behaves exactly as before. The default scheme has one level named `UNCLASSIFIED`, no compartments and one unnamed trust level; in that mode replies are the reference's, nothing on the request path consults labels beyond one predictable branch, and the `LABEL` and `CONTEXT` commands answer `ERR labels are not configured on this server` except for `HELP`.

## The scheme

```sh
./bin/eski --save '' --appendonly no \
  --label-levels 'UNCLASSIFIED,CONFIDENTIAL,SECRET,TOP SECRET' \
  --label-compartments 'A,B' \
  --label-trust-levels 'WEB,VETTED' \
  --label-audit-file /var/lib/eski/audit.log
```

`label-levels` lists up to 256 levels from lowest to highest, `label-compartments` up to 256 compartments and `label-trust-levels` up to 256 trust levels from lowest to highest; each value is a comma-separated list. A name has 1 to 64 bytes of letters, digits, `-`, `_` and single inner spaces, starts each word with a letter or a digit, and is folded to upper case. Levels and compartments share one set of names, trust levels have their own, and `CONTEXT` and `TOKEN` cannot name a level. An empty trust list means one unnamed trust level. The scheme is labelled as soon as it has more than one level, any compartment or more than one trust level.

A scheme can grow but never shrink. At startup each directive sets its list. Afterwards `CONFIG SET` may only rename names in place and append new ones; a list that is shorter, reorders names or reuses a name the scheme already had is refused with `label scheme names can be added and renamed, never removed or reordered` or `a renamed or added label name must be new to the scheme`. Because stored data refers to positions, a rename changes how every marking is written and nothing else. `CONFIG` is an administrative command, `CONFIG SET` and `CONFIG REWRITE` need a top label for every setting while a scheme is on (see [What is enforced in this release](#what-is-enforced-in-this-release)), the settings are hidden from `CONFIG GET *` like Eski's other settings that the 7.4 server lacks, `CONFIG REWRITE` writes them, and every change is written to the audit file. When snapshots are in use (save points or a shutdown save configured, or a snapshot written or loaded since the start), a rename or an extension at runtime first saves a snapshot with the changed scheme and answers `the snapshot with the changed label scheme could not be written; check the server log` without changing anything if that save fails; a running background save is stopped first, because it would write the old names. The configuration file still names the scheme it was started with, so run `CONFIG REWRITE` after a runtime change (or edit the file the same way): after a rename the next start otherwise refuses the snapshot, because the file and the configuration then name a position differently, while an extension is adopted from the file at the next start, with a log line and a `scheme-adopt` audit record per list that grew. The scheme settings cannot be changed while the server loads its data file.

Snapshots keep labels: `SAVE`, `BGSAVE`, the save points, the shutdown saves and `DEBUG RELOAD` write every copy with its label, its age among the other copies of its name and the label quotas, and a restart loads them back exactly ([Persistence](persistence.md#labels-and-owners) describes the file). The append-only file keeps them too: with `appendonly yes`, at startup or switched on with `CONFIG SET`, every record carries the scope of its change, `BGREWRITEAOF` and the automatic rewrite write a snapshot as the base, and a restart replays the base and the incremental files to the state the server had ([Persistence](persistence.md#the-append-only-file) describes the records, the rewrite, the forget rewrite, torn tails and what the loader refuses). The base is always a snapshot, so `aof-use-rdb-preamble no` stops the startup and is refused by `CONFIG SET` with `the append-only base of a server with a label scheme or owner mode is always a snapshot`. A scheme can be turned on while the log is on, on an empty server, and a runtime rename or extension of it rewrites the log before `CONFIG SET` answers, the way it saves a snapshot, so the files never hold names that the running scheme lacks (and a rewrite that fails refuses the change and leaves the log as it was). `BGREWRITEAOF` and `DEBUG LOADAOF` need a top label like `SAVE`. `MIGRATE` answers `ERR MIGRATE is off while a label scheme is configured; move keys with DUMP and RESTORE`: it would write at whatever login its cached connection to the target holds, so data moves between servers through `DUMP` and `RESTORE` from a client, which write at the scope of the command. A scheme is also refused while the memcached endpoint is on, because memcached requests carry no label.

A scheme starts on an empty server, because Eski never guesses a label for data that has none. Turning a scheme on with `CONFIG SET` is refused while the server holds any key in any database, vector sets and expired keys not yet removed included, with `a label scheme needs a server without keys, because existing keys carry no label`; growing or renaming a scheme that is already on is not affected, while adding a scheme to [owner mode](owners.md#owner-mode) without one counts as turning it on. A server started with a scheme never loads a data file written without one: when the file that `dir` and `dbfilename` name carries no labels, it exits at startup with `Refusing to start: the data file <name> in <dir> holds data that carries no labels or owners, and a server with a label scheme or owner mode never loads it`, followed by what to do, and `DEBUG RELOAD NOSAVE` answers `ERR Error trying to load the RDB dump, check server logs.` without touching the data it holds. Turning a scheme on with `CONFIG SET` while save points or a shutdown save are configured first writes an empty labelled snapshot, so the file on disk never holds unlabelled data that the next start would refuse. To adopt labels for existing data, start the labelled server empty and write the data into it with the labels it should carry, for example by reading each key from the old server and writing it through `LABEL AS` at its label; to keep the old data, start once without the scheme and move it out first, or move the file away.

## Markings and the order

A marking is written `LEVEL`, `LEVEL//COMPARTMENT/COMPARTMENT` or either of those followed by `;TRUST`, for example `SECRET//A/B;VETTED`. Input is case-insensitive and tolerates spaces around names; replies use the canonical form, with compartments in configuration order and the trust part left out at the lowest trust level. Commands also accept the trust as a separate `TRUST <name>` argument, but not both forms at once.

A reader at label r can read data at label d when r's level is at least d's, r's compartments include d's, and r's trust is at most d's. A trusted task therefore reads only data at its trust or higher, while an untrusted task reads everything its level allows. Every write lands exactly at the command's label, including its trust. A label is top when it dominates every label the scheme can form: the highest level, every compartment and the lowest trust.

## Logins

| Rule | Meaning |
| --- | --- |
| `clearance:<marking>` | the highest level and compartments the login may assert; `clearance:*` means the top of the scheme as it grows; without the rule a login has the lowest level and no compartments |
| `trust:<name>` | the highest trust the login may assert; `trust:*` means the highest trust level; without the rule a login has the lowest trust |
| `label-per-command`, `label-per-session` | require every command to arrive through `LABEL AS`, or allow commands that run at the session label (the default) |
| `require-token`, `token-optional` | accept only `LABEL AS TOKEN`, or also the other forms (the default) |
| `token-key:<64 hex digits>`, `reset-token-keys` | add an Ed25519 public key for signed levels, up to eight, or remove them all |

A space inside a marking or a name is written as `+` in these rules, for example `clearance:TOP+SECRET//A`, because ACL files separate rules by spaces; `ACL SETUSER` also accepts a real space inside one argument. The clearance is checked component by component and is not dominance: an asserted label is allowed when its level is at most the clearance's level, its compartments are among the clearance's and its trust is at most the trust rule. `ACL LIST`, `ACL SAVE` and `ACL LOAD` carry the rules, `ACL GETUSER` adds `clearance`, `trust` and `token-keys` fields and lists `label-per-command` and `require-token` among the flags, and `reset` clears them all. The rules are refused while no scheme is configured. An ACL change that leaves a connection's session, transaction label or monitor label outside the login's new clearance closes that connection, and an ACL change that removes a login drops its contexts.

The ACL checks commands and keys exactly as before; labels add to them and replace nothing. Rights over labels are ordinary subcommand rules: `CONTEXT CREATE` is the subcommand `context|create`, in the `@admin` and `@dangerous` categories only, so `+@all` and an explicit `+context|create` grant it while `+@all -@dangerous`, `+@all -@admin` and `+@slow` do not; an agent login should still carry `-context|create` when it is built from `+@all`. `+@all` does not let a login below top change the configuration: `CONFIG SET` and `CONFIG REWRITE` need a top label whatever the ACL grants (see What is enforced in this release), and a login that must not read the settings should carry `-config|get` too. The `CONTEXT` container itself has no category. The `LABEL AS` prefix itself is not checked by the ACL; the wrapped command is. The ACL check of the wrapped command, with its `NOPERM` reply and its `ACL LOG` record, runs before the label refusals of top-only commands and of persistence, so a login without the right to a command gets `NOPERM` as it does without labels; only the errors of the `LABEL AS` prefix itself and the label refusals that decide the command's label (a `label-per-command` or `require-token` login, a transaction at another label, an invalid label and a subscription that needs a session) come before it. A command with the wrong number of arguments gets that error before both.

## How a command gets its label

```text
LABEL AS SECRET//A GET doc:7
LABEL AS SECRET//A TRUST VETTED HSET doc:7 title draft
LABEL AS CONTEXT 3f1c...e9 VSIM memory ELE question
LABEL AS SECRET//A TRUST VETTED CONTEXT 3f1c...e9 GET doc:7
LABEL AS TOKEN 65736b...2e.9a77...01 GET doc:7
LABEL SESSION CONFIDENTIAL
LABEL WHOAMI
```

`LABEL AS` wraps exactly one command in the same request, so it is safe under pipelining and on pooled connections; the ACL checks the wrapped command and its keys. With a marking it runs the command at that label, with `CONTEXT` at the context's label, with a marking and `CONTEXT` only when they are equal, and with `TOKEN` at the label of a verified signed statement. `LABEL AS` cannot wrap `LABEL AS` or `LABEL SESSION`. Without a prefix a command runs at the connection's session label: the one set with `LABEL SESSION <marking> [TRUST <name>]`, or else the login's clearance level and compartments at the lowest trust. `RESET` and `AUTH` clear the session, and a connection's label state counts toward its client memory (`tot-mem` in `CLIENT LIST`). `LABEL WHOAMI` returns the login, the command's label as one text and as marking and trust, the clearance, the trust clearance, whether a session was set, the two login flags and whether the label is top.

Unknown names, names outside the clearance and a full label table all answer the same `ERR invalid label`, so the vocabulary cannot be probed. On a `label-per-command` login every other command is refused with `ERR this login must send every command through LABEL AS`, except `AUTH`, `HELLO`, `PING`, `ECHO`, `SELECT`, `QUIT`, `RESET`, `CLIENT SETNAME`, `CLIENT SETINFO`, `CLIENT ID`, `LABEL WHOAMI`, `LABEL HELP` and `CONTEXT HELP`, and `LABEL SESSION` answers `ERR LABEL SESSION is not available to this login`; a `require-token` login behaves the same way and accepts only `LABEL AS TOKEN`. Subscriptions and `CLIENT TRACKING ON` need a lasting label, because pushed messages carry no label of their own. Sent without a prefix on a connection that has no session, `SUBSCRIBE`, `PSUBSCRIBE`, `SSUBSCRIBE` and `CLIENT TRACKING ON` pin the session at the label they run at, the login's clearance level and compartments at the lowest trust, exactly as `LABEL SESSION` at that label would: `LABEL WHOAMI` reports the session, delivery, the `PUBLISH` and `PUBSUB` counts, `CLIENT LIST` and invalidations use it, and it stays after `UNSUBSCRIBE` and `CLIENT TRACKING OFF`. The pin is set only after the command passes the arity and `ACL` checks, so a subscription refused with `NOPERM` leaves the connection without a session. Inside a transaction whose `MULTI` had no prefix the command pins when `EXEC` runs it. To listen at a lower label, send `LABEL SESSION` first. Under a `LABEL AS` prefix, inside a transaction bound by a prefixed `MULTI`, and on `label-per-command` and `require-token` logins they still answer `ERR this command needs a session label set with LABEL SESSION`, because a prefix covers one command and must not set the connection's lasting label. An ACL change that leaves the pinned label outside the login's clearance closes the connection, as for any session. `AUTH` and `HELLO AUTH` to another login clear the session; a connection that still holds subscriptions or tracking is then pinned at the new login's label, or closed when the new login is `label-per-command` or `require-token`.

The SDKs of a later stage expose the label and the context as properties of a client, never as arguments of a call, so that a language model composing a command cannot choose its own label. Until then the application must add the prefix itself and must never let model output reach it.

## Transactions and scripts

A label on `MULTI` binds the transaction: queued commands run at that label whether or not they repeat it, a queued command with a different label is refused when it is queued with `ERR the command's label differs from the transaction's label` and the transaction is discarded at `EXEC`, and `EXEC` itself must carry the same label or none. Without a prefix, `MULTI` binds the session label. On a `label-per-command` login only `MULTI` needs the prefix. `LABEL SESSION` is not allowed inside a transaction.

`WATCH` records the label it runs at. When any key was watched at a label other than the transaction's label, `EXEC` runs nothing, answers `EXECABORT Transaction discarded because of: the command's label differs from the transaction's label` and clears the watches, whether or not a watched key has changed. Only the labels the connection used decide this, never the data: every `WATCH` since the watches were last cleared counts, including one sent after a watched key changed, and a write the transaction's label cannot see therefore never changes what its `EXEC` answers. The rule applies across `AUTH` and `HELLO AUTH`, which keep the watches, so a key watched at one login's label refuses the transaction of a login with another label, and a key watched before a scheme was configured at run time counts as watched at the lowest label. `EXEC`, `DISCARD`, `UNWATCH` and `RESET` clear the watches as without labels, and a transaction whose keys were all watched at its own label behaves exactly as before.

A write that a watch sees marks the transaction as it does without labels, but where the 7.4 server then forgets the connection's watched keys, a labelled server keeps every watched key until the watches are cleared: a `WATCH` sent after the mark still adds its keys, and a marked transaction still queues its commands. The `watch`, `multi`, `multi-mem` and `tot-mem` fields of `CLIENT LIST` and `CLIENT INFO`, the client memory that `maxmemory-clients` evicts by and the queued bytes that count against `client-query-buffer-limit` therefore depend only on the commands the connection sent, never on whether a watched key was written, and the `d` flag of a marked transaction appears only to a caller whose label is top or dominates the label of every key the connection watches.

Scripts and functions run at the label of the command that called them, and every `redis.call` inside them uses it. `LABEL AS`, `LABEL SESSION` and every `CONTEXT` subcommand except `HELP` are refused inside scripts, while `LABEL WHOAMI` shows the caller's label. While a script is busy, the commands other connections may still run (`SCRIPT KILL`, `FUNCTION KILL`, `FUNCTION STATS`, `AUTH`, `HELLO`, `MULTI`, `WATCH` and the rest) run at their own connection's label, including a `LABEL AS` prefix, and the script's label is restored afterwards. `FUNCTION STATS` shows the running function only to a caller whose label dominates the label the script runs at, and `SCRIPT KILL` and `FUNCTION KILL` need such a label, or else answer `ERR this command needs a label that dominates the running script's label`. In owner mode the caller also needs the script's own owner or the operator scope (see [Owners](owners.md#transactions-and-scripts)).

Scripts and stored functions are closed across labels. Changing stored functions, with `FUNCTION LOAD` (also with `REPLACE`), `DELETE`, `FLUSH` and `RESTORE`, and emptying the script cache with `SCRIPT FLUSH` need a top label; `FUNCTION LIST`, `DUMP`, `STATS`, `FCALL` and `FCALL_RO` stay available to every login. The script cache behaves as one cache per label: a cached script is visible only to a caller whose label dominates a label that loaded it with `EVAL` or `SCRIPT LOAD`, `EVALSHA`, `EVALSHA_RO` and `SCRIPT EXISTS` answer any other script as missing, `EVAL` and `SCRIPT LOAD` of it answer as a first load, and the 500-entry bound and its eviction apply per label. Each label has its own `math.random` stream, and every run starts with the engine's starting cjson and collector settings, so a run never observes what a run at another label did. Function code is installed by the operator and must not keep data between calls, because a library's closures survive every call at every label. [Scripts](scripting.md#labels-and-owners) gives the details.

## Contexts

```text
CONTEXT CREATE [LEVEL <marking>] [TRUST <name>]
CONTEXT INFO <handle>
CONTEXT DROP <handle>
```

A context fixes one label for one task, typically an agent's run on behalf of a user. `CONTEXT CREATE` returns a handle of 32 hexadecimal digits drawn from the operating system's random source and bound to the creating login. Its label is the creating command's label, with `LEVEL` replacing the level and compartments and `TRUST` the trust, and it must be within the login's clearance. Commands under the context read what its label dominates and write exactly at it. `CONTEXT INFO` returns the marking and the trust so that the application can stamp the agent's answer, and `CONTEXT DROP` ends the context. A handle from another login, an expired handle and an unknown or malformed handle all answer `ERR invalid context`, and a context whose label has left the login's clearance stops working. A context expires after `label-context-idle-timeout` seconds without use (default 3600), and a login holds at most `label-context-max-per-login` contexts (default 1000); both are operator settings.

## Signed levels

A signed level lets the application relay a label that a separate issuer signed, so that a compromised application can only replay labels it was given. The token is the hexadecimal encoding of a statement, a dot, and the hexadecimal encoding of the statement's 64-byte Ed25519 signature. The statement is text with one field per line:

```text
eski-label-token 1
marking SECRET//A
trust VETTED
expires 1767225600000
audience prod-node-1
context 3f1c0a5e6b7d8c9f0a1b2c3d4e5f6a7b
```

The header line, `marking`, `expires` (Unix time in milliseconds) and `audience` are required; `trust` and `context` are optional; each field appears at most once and any other line refuses the token. Eski accepts a token when its signature verifies with one of the login's `token-key` rules, the audience equals the `label-token-audience` setting (tokens are refused while it is empty), it has not expired, its label is within the login's clearance and, when it names a context, that context belongs to the login and has the same label. Any failure answers `ERR invalid label token`. Verified statements are cached by a hash of the login and the token, with the expiry and the clearance checked again on every use and the cache cleared by every ACL change. Tokens are issued by a signing tool or service that the operator runs with the private keys; Eski only verifies them.

## What is enforced in this release

| Channel | Rule |
| --- | --- |
| Pub/sub | a message carries the publishing command's label and reaches only subscribers whose session label dominates it; `PUBLISH` and `SPUBLISH` count the receivers at exactly that label; `PUBSUB CHANNELS`, `NUMSUB`, `NUMPAT`, `SHARDCHANNELS` and `SHARDNUMSUB` count only subscribers the caller dominates |
| Keyspace notifications | published through the same path with the label of the copy that changed, so they reach only sessions that dominate it |
| `MONITOR`, `LATENCY`, `SWAPDB`, `DEBUG`, `CLIENT PAUSE`, `CLIENT UNPAUSE`, `MEMORY STATS`, `DOCTOR`, `MALLOC-STATS` and `PURGE`, `SLOWLOG RESET`, `CONFIG SET`, `CONFIG REWRITE` and `CONFIG RESETSTAT`, `FUNCTION LOAD`, `DELETE`, `FLUSH` and `RESTORE`, `SCRIPT FLUSH` | need a top label, else `ERR this command needs a label that dominates the whole label scheme`; a monitor sees only commands its label dominates |
| `CONFIG SET`, `CONFIG REWRITE` | need a top label for every setting, because the configuration is one store for every label: a login at one label could write a value that a login at a lower label reads with `CONFIG GET`, and a setting such as `maxmemory` acts on the data of every label. The refusal is the one above and depends on the subcommand alone: it comes before any setting is looked at, so a setting that exists, a hidden one, an immutable one, a name that does not exist and a call with too few arguments all get the same answer and nothing changes. It holds in the same way inside `MULTI`, in a script and in a function, and behind the `LABEL AS` prefix. `CONFIG GET` and `CONFIG HELP` stay open to every login the ACL allows, so a login below top still reads the settings, the hidden ones by their exact names; give it `-config|get` when it must not |
| `SAVE`, `BGSAVE`, `BGREWRITEAOF` and `SHUTDOWN` in every form | need a top label, else the same error, because a save forks and writes every label's data; the settings that decide whether data at every label survives a restart, `save`, `appendonly`, `dir`, `dbfilename` and the rest, are covered by the `CONFIG SET` row above |
| `LASTSAVE` | below top answers the time the server started, because automatic saves follow a change counter that writes at hidden labels move; at top it answers the time of the last successful save |
| `DUMP` and `RESTORE` | `DUMP` serialises the copy the caller reads as an ordinary payload that carries no label; `RESTORE` writes at exactly the command's label under the write rule above, so it answers `INUSE` when the caller sees the name at another label and `REPLACE` replaces only the copy at its own label; it always checks the payload in depth, whatever `sanitize-dump-payload` says (see [Persistence](persistence.md#labels-and-owners)) |
| `FLUSHALL` | only a flush that removes every label's data stops a running snapshot and saves at once when save points are configured |
| `CLIENT PAUSE WRITE` | holds every command that the command table marks as a write, the vector set writes and `LABEL DECLASSIFY` included, and `EVAL`, `EVALSHA`, `FCALL`, `PFCOUNT`, `PUBLISH` and `SPUBLISH`, as the reference does; `OWNERS FORGET` runs during the pause and drops the forgotten user's held work (see [Threading](threading.md#vadd-with-cas)); it judges a command sent through `LABEL AS` by the command it wraps, exactly as that command unwrapped, also for `EXEC` and the scripts; the prefix is read without arrival's effects, so a held command changes no session, owner, context or token cache before it runs. A prefix that fails on its own, for want of a wrapped command, with a marking that does not parse or outside the login's clearance, or on a `require-token` login, answers its error at once; one whose owner, context or token is refused waits like the command it wraps and is refused after the pause. During the pause every `EVALSHA` waits (see [Scripts](scripting.md#labels-and-owners)) |
| `CLIENT LIST`, `CLIENT KILL`, `CLIENT UNBLOCK` | act only on connections whose session label the caller dominates; `CLIENT LIST` and `CLIENT INFO` show a marked transaction's `d` flag only to a caller that dominates the label of every key the connection watches |
| `SLOWLOG GET` and `LEN` | show only entries whose label the caller dominates |
| `INFO` | for callers below top, `connected_clients` counts the connections they dominate, the other numbers of the clients, memory, persistence, stats, replication and CPU sections are zero, `maxmemory` included, although `CONFIG GET` answers the configuration to every login the ACL allows, the status fields of the persistence section (`rdb_last_bgsave_status`, `aof_last_bgrewrite_status`, `aof_last_write_status`) read `ok` whether the last save failed or not, and the command, error and latency statistics are empty; the server section is unchanged except its compute and keyspace worker fields, which read zero apart from the configured worker counts, shown for the active counts as well (see [Threading](threading.md#runtime-observations)), and the keyspace section counts what the caller can see (see Keys) |
| Scripts and functions | run at the caller's label; the script cache, `SCRIPT EXISTS` and `EVALSHA` see only scripts loaded at labels the caller dominates, and `math.random` and the cjson settings stay within one label |
| `ACL LOG` | stays an administrative command |

The audit file named by `label-audit-file` is opened at startup, append-only with mode 0600, and receives one JSON line per event with the time in milliseconds, the login, the client id and address, the event and its details: `scheme-load` at startup, `scheme-change` with the list before and after, `scheme-adopt` with the list before and after when a data file extends the scheme at load, `acl-setuser` with the rules (password rules redacted), `acl-deluser`, `acl-load`, `declassify` with the key, the element and both labels (never values), and `label-quota`. The file holds one JSON record per line, so standard log tools can read, rotate, ship and search it.

While a scheme is configured every command runs on the coordinator; the keyspace workers stay idle.

## Keys

Every key of the ordinary types (strings, lists, sets, hashes, sorted sets and streams, with bitmaps, HyperLogLog and geo following their storage type) has one label: the label of the command that created it. A name can exist at more than one label; each such copy is an independent key.

A read returns exactly one copy: the copy at exactly the command's label if there is one, otherwise the highest copy the reader can see, ordered by higher level, then more compartments, then higher trust, then the older copy. A copy's age is the moment its name came into existence at its label: overwriting a copy keeps its age, while deleting and recreating it, or creating it by `RENAME`, `MOVE` or `COPY`, makes a new copy. A copy the reader cannot see behaves exactly like a missing key before any other check, so `GET` answers nil, `TYPE` none, `EXISTS` 0 and `TTL` -2, and a write of another type creates a new copy instead of answering `WRONGTYPE`.

A write lands exactly at the command's label. When the copy at exactly that label exists, the write applies to it as usual. When the writer can see a copy only at another label, the whole command is refused before any effect with `INUSE name in use at <label>`, which names the copy the writer would read; this covers creating, overwriting, changing and deleting, including `HSETNX`, `COPY` with `REPLACE`, and `RENAME`, `RENAMENX` and `MOVE` when the writer sees their source only at another label. A command that creates a name only when it is missing answers instead as it does without labels for a name that exists, reading the visible copy and changing nothing: a `SET` whose options parse and include `NX` answers nil, or with `GET` the visible copy's value or the type error, and `SETNX`, `MSETNX`, `RENAMENX` for its destination, `MOVE` for the name in the target database and `COPY` without `REPLACE` for its destination answer 0. When the writer can see no copy, the copy is created at the command's label and any hidden copy stays hidden. The check runs once per command from its key specifications, after the arity and ACL checks and before the command's own syntax and type checks; in a transaction it runs when `EXEC` reaches the command, and in a script for each `redis.call`. A task at `SECRET` therefore cannot change or delete its own `UNCLASSIFIED` keys; that is intended. Multi-key commands read their sources as reads and write their destinations as writes, and `SORT BY` and `GET` read hidden keys as missing.

A read of a copy at another label never changes it: it does not touch the copy's access time or frequency, does not delete it when expired, does not delete expired hash fields and does not write the HyperLogLog cardinality cache. `OBJECT IDLETIME` and `OBJECT FREQ` therefore count only accesses made at the copy's own label.

Listings and counts show each name once. `SCAN`, `KEYS` and `RANDOMKEY` walk one dictionary per label the reader can see; a name with copies at several visible labels appears only at the copy a read resolves to. A labelled `SCAN` cursor holds the position among the labels the reader can see that have held keys in the database and an exact position in that label's hash space, so cursor values and the keys of each call depend only on visible data, and a label that appears during a scan can repeat keys but never skip one. `RANDOMKEY` draws a visible key uniformly, retries only on visible keys that are shadowed by another copy or expired, and after 100 draws falls back to an exact pass over the visible labels, so it answers nil only when the reader can see no live name; while a write pause holds expiry it then draws among the visible expired names, as it does without labels. `DBSIZE` and the keys and expires of `INFO keyspace` keep the per-database meaning they have without labels (keys present in the table, including expired keys not yet reaped) and are summed over the visible labels, minus the extra copies of names held at more than one visible label; `avg_ttl` is the average over the visible labels weighted by their timed keys.

`FLUSHDB` and `FLUSHALL` delete only the keys at exactly the command's label, in the selected database or in every database; at a top label they delete everything. `SWAPDB` needs a top label and swaps every label of both databases. In owner mode a flush follows the owner its command names, as described in [Owners](owners.md#flushdb-and-flushall).

`WATCH` is aborted by a write at any label the watching command's label dominates, and never by a write at a hidden label; a transaction at another label than its watches is refused at `EXEC` (see Transactions and scripts), so an abort only ever reaches a transaction at the label its keys were watched at. A blocking pop or move waits on the name at exactly its own label, because that is the only copy it can change; `XREAD` and other read-only blocking commands wake on a write at any label they dominate. A keyspace notification carries the label of the copy that changed, and client tracking invalidations, including broadcast mode and the invalidation that follows a flush, reach only clients whose session label dominates that label.

Random draws (`RANDOMKEY`, `SRANDMEMBER`, `SPOP`, `HRANDFIELD`, `ZRANDMEMBER`, `VRANDMEMBER`, the frequency counter of the LFU policies and the levels of new graph nodes) come from one stream per command label, so commands at other labels never shift a draw. The streams are seeded from the label and a secret drawn at startup; the hidden startup setting `label-stream-seed` fixes the secret for tests. In owner mode the stream is per label and owner.

Each label of a database is its own dictionary with its own value storage, and the hidden startup setting `label-partitions-max` (default 1024) bounds how many of them the server holds across all databases: a write that needs a new one beyond the limit answers `ERR label partition limit reached`, and reads never create one. In owner mode these are the shared partitions; each user's keys at a label form an owner partition of their own, which this limit does not count (see [Owners](owners.md#keys)).

## Vector sets

A vector set element carries the label of the command that wrote it, and each label in a set is its own index. A set is present at each label where it holds elements, so a reader sees the set exactly when it can see one of its elements, and its view is the set's visible elements, one copy per element name by the same order as keys. Searches run over every visible label and merge exactly by score, then by name. `VADD` into a set the writer can see adds the element at the writer's label; a name the writer can see only at another label answers `INUSE element in use at <label>`, as do `VREM` and `VSETATTR` for an element the writer can see only elsewhere. A set present at a label the writer cannot see stays hidden, so a lower writer can create any type under the same name at its own label.

`DEL`, `UNLINK`, expiry, eviction and `FLUSHDB` at a label remove only that label's elements, and `EXPIRE` sets a deadline for that label's part only. `RENAME` and `MOVE` move only the elements at the command's label into a set of their own. `COPY` of a vector set is refused as it is without labels. `MEMORY USAGE` and `DEBUG OBJECT` report the reader's view. `DUMP` returns the reader's view as a flat payload without a graph, with the visible elements numbered in view order, so its bytes depend only on what the reader sees; `RESTORE` of any vector set payload builds a new set at the command's label, as it would build a key of another type, and a set whose other partitions live at other labels keeps them, as with `RENAME`. Snapshots keep every partition of a set with its graph, its free slots and the age of each element among its copies, and a restart answers every vector read at every label as before (see [Persistence](persistence.md#labels-and-owners)). A scheme cannot be turned on while a set exists (see The scheme), so every set of a labelled server holds elements written under labels. Compared with the same writes without labels, `VSIM` orders every group of equal scores by element name, where without labels it orders the group by insertion, so the members returned differ only when such a group straddles the `COUNT` cut, and `VRANDMEMBER` draws from the reader's per-label stream.

## Key commands

| Command | Rule |
| --- | --- |
| `LABEL OF key [element]` | the label of the copy, or of the vector set element, that a read resolves to, or nil; in owner mode followed by ` SHARED` or ` OWNER <id>` |
| `LABEL DECLASSIFY key <marking> [TRUST <trust>] [ELEMENT <element>]` | moves the copy at exactly the command's label, or one of its vector set elements, to a label the command's label dominates, keeping value, expiry and access time; follows the write rule at the target, so it is refused with `INUSE name in use at <label>`, or `INUSE element in use at <label>` for an element, whenever the target label can see a copy of the name or element, at itself or at a label it dominates, naming the copy a read at the target resolves to; a successful move equals deleting at the command's label and writing at the target, done at once; needs the `label|declassify` right and writes a `declassify` audit record |
| `LABEL COPIES [key]` | needs a top label; the names held at more than one label in the selected database, or every copy of one key with its type, for cleanup; in owner mode `LABEL COPIES [OWNER <id> \| SHARED] [key]` lists one scope, `SHARED` by default, and adds the scope suffix to each copy |
| `LABEL QUOTA <marking> [TRUST <trust>] [LIMIT <bytes>]` | needs a top label; shows the quota and the bytes held at exactly that label across all databases, or sets the quota (0 removes it) |

`LABEL OF` is in the `@fast` and `@connection` categories. `DECLASSIFY`, `COPIES` and `QUOTA` are the subcommands `label|declassify`, `label|copies` and `label|quota`, in the `@admin` and `@dangerous` categories only, like `CONTEXT CREATE`, so `+@all` and an explicit rule such as `+label|declassify` grant them while `+@all -@dangerous`, `+@all -@admin`, `+@slow`, `+@write` and `+@keyspace` do not. The `LABEL` container itself has no category, so of the `LABEL` subcommands `+@slow` grants only `LABEL HELP`. An agent login built from `+@all` should still carry `-label|declassify`.

This release has no command that moves data up. A move up would have to answer whether the higher label already holds the name, which a command below that label must not learn, so data is raised by deleting it at the lower label and writing it at the higher one.

A quota bounds the keys, values and dictionary memory at exactly one label; in owner mode it counts shared data only, and users are bounded by owner quotas instead. For a vector set a label is charged for its own part of the set only, by a fixed formula over that part: the set's own header and tables as if the part were the whole set, its elements with their names and attributes, the room its vectors and element tables have grown to, and for a graph its node tables and levels. The charge never depends on the parts other labels hold, on which part was written first, on what else the server allocated or on a restart, and it is at least what the part's own memory and the set's header hold. The one figure that is an allowance and not a bound is the element's entry in the set's name index, 40 bytes plus the name's length: the index can hold more than that: up to twice the allowance for names near 1,000 bytes as soon as they are inserted, a few percent of the charge with random names of 120 bytes, and up to about three times the allowance after most of a set's names were removed. A set that holds parts at several labels has its header charged to each of them, so the charges of its parts add up to more than the set holds; the server's memory, `maxmemory` and eviction count what the set really holds. A part's charge does not fall back when elements are removed from it: the names and attributes of the removed elements leave the charge, but the room its vector area and tables grew to stays allocated and stays charged. A graph's tables leave the charge when the part shrinks to 128 elements, and the rest returns only when the part itself goes, with its last element or when the key is deleted, expires or is evicted at that label; a label at its quota makes room by removing keys, not elements. `MEMORY USAGE` below top is the same formula summed over the parts the reader sees. Before a command that can grow memory runs at a label over its quota, Eski evicts keys at that label only, with the configured `maxmemory-policy`, until the bytes the quota counts for that label are within it; it refuses the command with `OOM command not allowed when used memory > 'label-quota'.` only when nothing at the label is left to evict and the label is still over. Which keys go and whether the command is refused depend on that label's own data alone. `maxmemory` still applies to the whole server; without quotas for every label in use, global eviction and `OOM` remain a channel between labels.

## What the labelled gate records

The [labelled-mode gate](build-run-test.md#labelled-mode-gate) runs the 7.4.11 suite, its scripting unit, the vector set unit, the vector set reply comparison and smoke against a server with three levels, two compartments and two trust levels whose default login is top, in both worker modes, and accepts only the differences from labels-off that `test/labelled/expected` lists by name, each with its cause:

| Category | Cause |
| --- | --- |
| append-only-file | `CONFIG SET aof-use-rdb-preamble no` is refused while a scheme is configured, because the base of the append-only file is always a snapshot (see [Persistence](persistence.md#the-append-only-file)); the suite's tests that switch the preamble off differ, and so do the tests behind a server block that starts with that setting, which the refusal ends together with its unit, while smoke's check that switches it off differs, as do its check of `CONFIG GET` and `SET` of every parameter in that one parameter, its check of the file names after two rewrites, which finds a snapshot base, and the four checks that read the end of the log as plain commands, because every record starts with the scope of the change |
| migrate | `MIGRATE` is refused while a scheme is configured (see The scheme), so smoke's two scripted `MIGRATE` comparisons differ in every case whose reply, counters or later state the refusal changes, and so do its single `MIGRATE` checks and its `MONITOR` check, which does not show the refused commands |
| restore-validation | `RESTORE` always checks its payload in depth while a scheme is configured (see [Persistence](persistence.md#labels-and-owners)), so smoke's cases that restore, with `sanitize-dump-payload no`, an intset whose members are out of order or a set with a repeated member answer `ERR Bad data format` |
| reload-merge | `DEBUG RELOAD MERGE` and `NOFLUSH` are refused while a scheme is configured (see [Persistence](persistence.md#labels-and-owners)) |
| debug-digest-scopes | while a scheme is configured `DEBUG` offers `DIGEST-SCOPES`, one signature over every copy with its scope, deadline and age, every vector set partition and the quotas, and `DEBUG HELP` lists it, so smoke's check of the help lines finds three lines the 7.4 server does not have |
| logins | a login created without a clearance rule runs at the lowest label (see Logins), where it sees no top data, no statistics and no top-only commands, cannot have its copies changed from the top label and waits on names at its own label; smoke's permissions scenario, which writes keys and publishes as the default login at the top label and then reads and subscribes as new logins, finds nothing in either protocol |
| acl-output | `ACL GETUSER` and `ACL LIST` carry the label rules, and the listing of users at the end of smoke's ACL scenarios shows the default login with the rule the gate gives it |
| memcached | the memcached endpoint is off while a scheme is configured |
| watches | a labelled server keeps a marked transaction's watched keys and its queue until the watches are cleared (see Transactions and scripts), so smoke's introspection scenario, which writes keys its connections watch and then reads the watch fields of `CLIENT LIST` and `INFO`, differs from the 7.4 server |
| pause-scripts | during `CLIENT PAUSE WRITE` a labelled server holds every `EVALSHA`, because whether a cached script is read-only cannot be looked up before the command's label is known (see [Scripts](scripting.md#labels-and-owners)); the pause unit's read-only `EVALSHA` test waits until the suite gives up, which ends the unit before its later tests |
| wrapper | the gate declares the default login and the scheme on the command line, which conflicts with ACL files and configuration files that declare users, and which `CONFIG REWRITE` then writes into a configuration file that the reference server cannot load |

The suite differs in 94 tests: 16 for append-only-file (the two tests of the other unit that switch the preamble off, the two rewrite tests of the stream unit and the two help tests behind them, and ten tests of the stream consumer group unit, from its first server block that switches the preamble off on), 68 for logins, most of them later tests of the acl unit, which waits for a push that a lower login's blocking pop never sees, and 10 for pause-scripts, the read-only script test of the pause unit and the 9 tests after it. The scripting unit differs in 14 tests, all for logins, because the unit's Script ACL check leaves its connection authenticated as a login without a clearance rule, so the function variant of each later test in that server block gets the top-only refusal for `FUNCTION LOAD`. The vector set unit and the reply comparison do not differ, as snapshots, `DEBUG RELOAD`, `DUMP` and `RESTORE` of vector sets work with a scheme. Smoke differs in 124 named checks: 82 for migrate, 10 for acl-output, 8 for restore-validation, 8 for memcached, 7 for append-only-file, 3 for wrapper, 2 for logins, 2 for watches, and 1 each for reload-merge and debug-digest-scopes. The gate gives the default login back its rules after each reset in the ACL scenarios, so smoke's function scenario and persistence section run at the top label, and the persistence section differs only in reload-merge. Subscriptions and tracking pin the session on their own and are not among the differences, and since the ACL check runs before the top-only refusal a lower login without a right gets the same `NOPERM` as without labels.

The gate's three owner modes run the same runners with [owner mode](owners.md#owner-mode) on: `owners-shared`, whose default login has the operator scope and no owner rule, so the suite's data is shared; `owners-user`, whose default login is the one user `suite-user` with the operator scope; and `owners-only-user`, the same login without a label scheme. Their files under `test/labelled/expected/MODE/` keep the categories above, with reasons that add the owner rules: a login without an owner rule acts as `SHARED` without the operator scope, `ACL GETUSER` and `ACL LIST` also carry the owner rules, the top-only commands need the operator, every record of the append-only file also names the owner of a change made for a user, and `MIGRATE` and the memcached endpoint stay off in owner mode with or without a scheme, with texts that name owner mode when there is no scheme. Four categories are new:

| Category | Cause |
| --- | --- |
| info-owners | `INFO` gives the operator an `# Owners` section (see [Owners](owners.md#server-wide-channels)), which the default, all and everything selections include, and its persistence section gives the operator the forget fields `owners_forget_sequence`, `owners_forget_in_snapshot` and `owners_forget_in_aof` (see [Owners](owners.md#persistence-and-forgetting)), so smoke's checks of the sections and layouts `INFO` returns differ from the 7.4 server |

| narrowed-flush | a flush that acts for a user removes only that user's keys (see [Owners](owners.md#flushdb-and-flushall)), and only a flush that removes everything stops a running snapshot and saves at once when save points are configured, so with the user `suite-user` as the default login the keys that logins without an owner rule wrote as `SHARED` survive every flush, and five of them reach every later unit of the suite and the persistence section of smoke, because the gate restarts the server in one directory and the server saves at shutdown and loads at start; smoke's checks of key counts and of an empty dataset in that section differ, as do its checks of the change counter after a flush and of a restart after it, and in the suite the tests that count keys, wait for the keyspace to empty or wait for a flush to stop a snapshot child differ |

In all three owner modes the scripting unit, the vector set unit and the reply comparison differ in exactly the tests and steps that differ in labelled mode, with the same counts, and so does the suite in `owners-shared`; the suite's logins that have no owner rule act as `SHARED` without the operator scope, and that reaches the same tests as the lowest label does. In `owners-user` and `owners-only-user` the suite differs in 9 more tests, all for narrowed-flush, because their data belongs to the user. Smoke differs in the checks it differs in labelled mode and in 12 more for info-owners, and in `owners-user` and `owners-only-user` in 9 more for the same reason: 3 for memory-figure, 5 for narrowed-flush and 1 for owner-tables.

## What comes next

The owner id per command, which adds per-user privacy beside the label, is built: [Owners](owners.md) describes it with its keyspace and vector set sides, its compact per-user partitions and the limits of its guarantees. The stages after it, in order:

- the rest of persistence with labels and owners: labelled and owner commands on the keyspace workers;
- the search commands, with their statistics kept per user;
- simulation testing of durability and a change log;
- the SDK helpers that send the label and the owner with each request and stamp them on ingested data.

Some things remain observable across labels:

- timing, including the time to create a key, which probes the dictionaries of hidden labels;
- memory pressure and eviction without quotas: quotas apply per label, but `maxmemory` and the eviction totals include the keys of hidden labels;
- the tracking table limit, the shared slow log capacity and its entry ids, and connection ids;
- the server-wide `label-partitions-max` limit, so a write can be refused because of partitions created at hidden labels;
- the exact write at which a label quota refuses or evicts, because a quota counts the allocator's usable sizes, which hidden data can move by a few bytes; `MEMORY USAGE` below top is computed from the key's own content instead and does not move;
- the server's configuration, which is one store for every label: `CONFIG GET` answers every login the ACL allows, below top included, so a login at any label reads the settings, `maxmemory` among them; give `config|get` only to logins that may know them (writing a setting needs a top label, see What is enforced in this release);
- the disk, in the same class as memory: a snapshot and the append-only file hold every label's data, so their sizes, the time a save or a rewrite takes, when the automatic rewrite starts and a failed save or write depend on hidden data, and after a failed background save `stop-writes-on-bgsave-error` makes writes at every label answer `MISCONF`; below top the `aof_` fields of `INFO` read as zero and none of them, no reply, no notification and no log line moves because a rewrite wrote hidden data;
- the `BUSY` replies that every connection gets while a script runs, whatever the script's label;
- counts that include expired keys not yet removed, such as `DBSIZE` and `INFO keyspace`, because active expiry removes them at one pace that all labels share;
- the label table, which holds at most 65,535 labels: a login with a wide clearance can fill it by naming many labels, after which every new label answers `ERR invalid label` for everyone;
- the shared Lua engine state listed under [Scripts](scripting.md#labels-and-owners): the heap counts of `collectgarbage` and `gcinfo`, when the shared collector runs, the `lua-max-memory` limit over the whole engine, the addresses that `tostring` prints and `os.clock`;
- whatever a stored function keeps in its closures between calls, which is why function code must not keep data.

Reads at another label leave no trace, which has one cost: shared data that lower labels only read looks unused to the eviction policy, so under an LRU or LFU policy it can be evicted first. Where that matters, give the labels quotas or use the `noeviction` policy.
