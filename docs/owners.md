# Owners

Owners add per-user privacy to [labels](labels.md). Every request names the end user it acts for, its owner, and one user's private data never reaches another user. An owner is the application's own user id, such as `u42`, `auth0|5f3c` or a UUID. `SHARED` is data that belongs to no user and that every user's commands can read. A command runs at a scope, a label and an owner, and a reader sees a copy when its label dominates the copy's label and the copy is shared or its own.

This release builds who is asking (the owner mode switch, the ways an owner arrives with a command, the login rules, the refusals, the transaction, watch, script and push bindings, the operator, the server-wide channels and the `OWNERS` command) and where the data lives: every key and vector set element is stored at the scope of the command that wrote it, each user's data is its own small partition, and another user's copy behaves exactly like a missing key.

## Owner mode

```sh
./bin/eski --save '' --appendonly no --memcached-port 0 --owners yes \
  --label-levels 'UNCLASSIFIED,CONFIDENTIAL,SECRET' \
  --user default on nopass '~*' '&*' '+@all' 'clearance:*' owner-operator
```

The hidden setting `owners` is `no` by default and turns owner mode on at startup or with `CONFIG SET owners yes`. Like a label scheme it never turns off: `CONFIG SET owners no` answers `owner mode cannot be turned off`. Turning owner mode on at runtime needs the memcached endpoint off, and is refused otherwise with `owner mode needs the memcached endpoint off, because its requests carry no owner`; with the append-only file on, the log is rewritten in the new mode before the answer (see [Persistence](persistence.md#the-append-only-file)). Once owner mode is on, `CONFIG SET` and `CONFIG REWRITE` need the operator at top like the other top-only commands (see [The operator and top](#the-operator-and-top)), so a login that turns owner mode on at runtime and goes on changing the configuration needs `owner-operator` first, given by an ACL change. While owner mode is on, `MIGRATE` is refused with `ERR MIGRATE is off while owner mode is on; move keys with DUMP and RESTORE` (or the label text when a scheme is configured), and `BGREWRITEAOF` and `DEBUG LOADAOF` need the operator at the top label. The append-only file keeps owners: its records carry the owner of each change, a rewrite writes an owner-mode snapshot as the base and a restart replays them. Snapshots keep owners, as described under [Persistence and forgetting](#persistence-and-forgetting). The words `OWNER` and `SHARED` become reserved: owner mode is refused on a scheme with a level of either name (`owner mode needs a label scheme without a level named OWNER or SHARED`), and while it is on no level can be added or renamed to them. Turning it on writes an `owners-on` audit record. Owner mode starts on an empty server, as a label scheme does: `CONFIG SET owners yes` is refused while the server holds any key in any database, vector sets included, with `owner mode needs a server without keys, because existing keys carry no owner`, and a server started with owner mode exits at startup when the data file that `dir` and `dbfilename` name was written without owner mode, saying why (see [Labels](labels.md#the-scheme)); `CONFIG SET owners yes` with save points configured first writes an empty owner-mode snapshot. To adopt owners for existing data, start the server empty in owner mode and write each user's data again through `LABEL AS OWNER <id>`, and shared data through `LABEL AS SHARED`; to keep the old data, start once without owner mode and move it out first, or move the file away.

Owner mode works with or without a label scheme. It turns on the protected mode of labels in either case: commands run on the coordinator, the memcached endpoint stays off, the append-only file records the owner of each change, introspection below top is filtered and push features pin their scope. With the default one-level scheme every command's label is top, so top in owner mode also needs the operator scope described below.

The settings `owner-quota-default` (bytes, 0 for none) and `owner-partitions-max` (0, meaning no limit) are hidden like the label settings, readable by exact name and written by `CONFIG REWRITE`. Their effect is described under [Quotas and memory](#quotas-and-memory). Two more hidden settings are fixed at startup. `owner-compact` (default `yes`) keeps the compact partition form described there; `no` gives every partition the larger fixed form instead, with the same replies, and exists only as an escape hatch. `debug-hash-seed` (default 0, meaning none) is a test setting that fixes the key and field hash seeds and the server's random start, so two test servers lay out the same keys alike; the server refuses to start with it unless `enable-debug-command` is `yes` or `local`, and it must never be set in production, because predictable hashes invite hash flooding.

With owners off, Eski answers exactly as without this feature, in both labels-off and labelled mode, apart from the order of the ACL check in labelled mode described in [Labels](labels.md#logins) and two exceptions: the `OWNERS` command exists and answers `ERR owners are not enabled on this server` except for `OWNERS HELP`, and the owner login rules answer `Owners are not enabled on this server` instead of a syntax error. `CONFIG GET owners` and the two other settings also answer by exact name. The words `OWNER` and `SHARED` in `LABEL AS`, the `OWNER` and `SHARED` options of `CONTEXT CREATE` and owner lines in signed tokens fail exactly as before, as an unknown command, a syntax error and a refused token.

## Owner ids

An owner id is 1 to 128 bytes of printable ASCII other than space, compared byte for byte. The id `*` is reserved: the login rule `owner:*` is refused as an invalid owner rule and `OWNER *` answers `ERR invalid owner`, while `owners:*` keeps its meaning of any owner. Inside, Eski interns each id into a 32-bit number in the order of first use, the first command that names it, a read included. A number is never reused while the server runs and never appears in a reply, an error or an audit record; the text does. `OWNERS FORGET` drops an id, and a later use of it starts afresh. Ids appear in audit records, ACL files and error texts, and every id that is ever named, even by a read, keeps an entry of about 0.2 KiB until it is forgotten, so applications should pass opaque ids such as UUIDs or database keys, never e-mail addresses or other personal data.

## Logins

| Rule | Meaning |
| --- | --- |
| no owner rule | every command runs as `SHARED`, as before; naming a user owner is refused |
| `owners:*` | the login may act for any owner and must name one with every command except housekeeping |
| `owner:<id>` | the login always acts for that one owner; its commands need no prefix and naming another owner is refused |
| `owner-shared` | an `owners:*` or `owner:<id>` login may also run commands as `SHARED`, by naming `SHARED`; without it such a login cannot act on shared data |
| `owner-operator` | the operator scope: top in owner mode, the full introspection and the `OWNERS` commands |

`reset` clears the owner rules with every other rule, and the rules are refused while owners are off. `ACL LIST`, `ACL SAVE` and `ACL LOAD` carry them, and in owner mode `ACL GETUSER` adds an `owners` field (`*`, the id or empty) and lists `owner-shared` and `owner-operator` among the flags. An owner id in a rule needs no escaping, because it holds no space. A login without an owner rule may name `SHARED`, its only scope. An ACL change that leaves a connection's pinned owner, its transaction's owner or the owner of a key it watches outside what the login may now act for closes that connection, as does removing the operator scope from a login whose connection runs `MONITOR`.

## How the owner arrives

```text
LABEL AS SECRET OWNER u42 GET note
LABEL AS SECRET TRUST VETTED SHARED HGET doc:7 title
LABEL AS OWNER u42 GET note
LABEL AS SHARED GET catalog
LABEL AS OWNER u42 CONTEXT 3f1c...e9 VSIM memory ELE question
LABEL AS CONTEXT 3f1c...e9 GET note
LABEL AS TOKEN 65736b...2e.9a77...01 GET note
```

`LABEL AS <marking> [TRUST <trust>] [OWNER <id> | SHARED] [CONTEXT <handle>]` runs the wrapped command at that label for that owner. `LABEL AS OWNER <id>` and `LABEL AS SHARED` take the label from the connection's session, as an unprefixed command does, and count as unprefixed for the label rules: a `label-per-command` login is refused outside a transaction unless the command is housekeeping, and a `require-token` login accepts them only for housekeeping. With a `CONTEXT` tail the context's label must equal the session label, and a `require-token` login refuses the form. `LABEL AS CONTEXT <handle>` takes the label and the owner from the context, and `LABEL AS TOKEN` takes them from the token. `LABEL SESSION` takes no owner: there is no connection-wide owner except the push pin below.

The commands that need no owner on an `owners:*` login are `AUTH`, `HELLO`, `PING`, `ECHO`, `SELECT`, `QUIT`, `RESET`, `CLIENT SETNAME`, `CLIENT SETINFO`, `CLIENT ID`, `LABEL WHOAMI`, `LABEL HELP`, `LABEL SESSION`, `CONTEXT HELP` and `OWNERS HELP`; every other command answers `ERR this login must name an owner with every command` unless it names one or runs inside a transaction whose `MULTI` named one.

| Refusal | Cause |
| --- | --- |
| `ERR invalid owner` | a malformed id, an id the login may not act for, `SHARED` without the right, or a full owner table; one text for all, so a fixed-owner login cannot probe which ids exist |
| `ERR this login must name an owner with every command` | an unprefixed command of an `owners:*` login |
| `ERR the owner differs from the context's owner` | an explicit owner or `SHARED` that disagrees with the context it names |
| `ERR this connection is bound to another owner` | a named owner other than the connection's pinned owner |
| `ERR invalid context` | a context whose owner the login may no longer act for |
| `ERR invalid label token` | a token whose owner the login may not act for, a token without an owner line on an `owners:*` login, or a token whose context has another owner |

The arity and ACL checks of the wrapped command and its keys run first, with `NOPERM` and the `ACL LOG` record, then the label refusals of top-only commands and persistence and then these owner refusals. The refusals that decide which command runs and at which label come before them, as in labels: the errors of the `LABEL AS` prefix itself, the refusals of `label-per-command` and `require-token` logins, a transaction at another label, an invalid label and a subscription that needs a session (see [Labels](labels.md#logins)). A command that does not exist answers the unknown-command error whatever its owner.

## Keys

Every key lives at exactly one scope, the label and the owner of the command that created it, and each user's keys at a label form a small partition of their own, created by the first write there and released when it empties. Owner partitions keep their keys and values on the heap and their small tables in single heap blocks, so they need no mapping of their own and idle partitions cost no CPU: expiry, field expiry, rehashing and type maintenance visit only the partitions that have such work due, and eviction picks among owners in constant time. Type maintenance, the incremental migration of a large hash, set or sorted set dictionary, takes at most 16 steps for each owner partition in a tick, while shared partitions share a budget of up to 64 steps a tick, so the same migration finishes later in a user's partition than in shared data; the work always completes, and like all timing its pace is outside the guarantees.

A command for user `o` at label `r` sees a copy at label `d` and owner `w` when `r` dominates `d` and `w` is `SHARED` or `o`; another user's copy behaves exactly like a missing key, before any type check. When several visible copies share a name, a read returns one of them, in this order:

1. the user's own copy at exactly `r`;
2. otherwise the shared copy at exactly `r`;
3. otherwise the highest visible copy by the label order of [Labels](labels.md#keys) (higher level, then more compartments, then higher trust), the user's own copy before the shared one at equal rank, then the older copy within one scope.

A user without private data therefore reads exactly like a shared reader at the same label, and after `OWNERS FORGET` the user's reads equal the shared view. The rule matters with trust: a reader at `C` sees `C;VETTED` data, so a user's own copy at `C;VETTED` loses to the shared copy at exactly `C` for that reader, while a reader at `S` gets the own copy. A read never changes a copy at another scope: no access-time or frequency update, no lazy expiry, no field reaping and no cached HyperLogLog count, so `OBJECT IDLETIME` and `FREQ` count only accesses at the copy's own scope.

Every write lands at exactly the command's label and owner. When the writer sees the name only at another of its own labels or only as shared, the whole command is refused with `INUSE name in use at <label> SHARED` or `INUSE name in use at <label> OWNER <id>`, where the text after `at` is a valid `LABEL AS` head and the id is always the caller's own. Create-only forms (`SET NX`, `SETNX`, `MSETNX`, `RENAMENX` for its destination, `MOVE` for its target and `COPY` without `REPLACE`) give their normal already-exists answer instead. A shared writer never sees private copies, so creating a name a user also holds succeeds and every user keeps its own copy. `LABEL OF` ends with the same ` SHARED` or ` OWNER <id>` suffix in owner mode, for every caller. `LABEL DECLASSIFY` keeps the owner, `RENAME`, `MOVE` and `COPY` stay within the command's owner, and `COPY` from a visible shared source into the user's own scope is allowed, being a read and a write. No command changes an owner: data moves between users or into shared data only by a read and a write. `SWAPDB` is operator only and swaps the owner partitions with the databases.

`DBSIZE`, `INFO keyspace`, `KEYS`, `SCAN` and `RANDOMKEY` show each visible name once, counting the user's own partitions and the shared partitions at visible labels; the work is bounded by the user's own data and the shared data the user can see, never by the number of owners. `RANDOMKEY` draws uniformly over the visible names from the scope's own random stream. For a user reader the `SCAN` cursor is an unsigned 64-bit number sent as text, as every cursor is: bit 63 is always clear, bits 48 to 62 hold an ordinal, bits 1 to 47 a position and bit 0 the phase, which is 0 while the scan walks the user's own labels in the database and 1 while it walks the shared labels. The user's own labels in a database are those where a partition of the user was ever created there since the user was last forgotten: by a write that passed the write rule and the partition limit and left the new partition holding a key when the command ended, by `MOVE` or `COPY` into the database and by `LABEL DECLASSIFY` to that label. A command that creates a partition and leaves it empty, one that the quota or the command itself refused or that changed nothing among them, leaves the set and the records behind it as they were before the command. Only `OWNERS FORGET` empties the set, and `SWAPDB` exchanges the sets of the two databases. The scan walks the labels of the set that the reader dominates, in label order, the ordinal counts within that filtered list, and a label whose partition was released scans as empty, so the cursor never depends on the user's data at labels the reader cannot see. A scan can return a name twice but never misses one that stays present, across partition releases and `OWNERS FORGET` included, and cursor values depend only on data the caller can see. Shared readers and label-only servers keep the labels cursor unchanged. The price of this rule is a small record: a user that deleted all of its data keeps 128 bytes for each database it wrote in, and a few bytes more for each further label it wrote at, counted in its quota use and in `OWNERS INFO` bytes, until `OWNERS FORGET`, while `OWNERS LIST` and `owners_holding_data` no longer count it.

`LABEL COPIES [OWNER <id> | SHARED] [<key>]`, operator at top, lists the names held at more than one label within one scope, `SHARED` by default, or the copies of one name in that scope with their scope suffix; there is no listing across owners.

Random draws (`RANDOMKEY`, `SPOP`, `SRANDMEMBER`, `HRANDFIELD`, `ZRANDMEMBER`, `VRANDMEMBER`, skiplist levels, frequency counters, graph levels and quota eviction sampling) come from one stream per scope, seeded from the label, the owner's id and the server's startup secret, so another user's draws never move a visible draw. A scope's stream is stored only once a command has drawn from it; a command that draws nothing allocates nothing.

### FLUSHDB and FLUSHALL

What a flush deletes depends on how the command names its owner:

| The flush | Below a top label | At a top label |
| --- | --- | --- |
| acts for a user: `OWNER <id>`, a context or token with that owner, or an `owner:<id>` login | that user's keys at exactly the command's label | that user's keys at every label |
| names `SHARED` explicitly, or comes from a non-operator login without owner rules | the shared keys at exactly the command's label | the shared keys at every label |
| comes from an operator (a login with `owner-operator` and no owner rule) that names no owner | the shared keys at exactly the command's label | everything: every user and the shared data |

Only the last case at a top label deletes every user's data. An `owners:*` login must name an owner or `SHARED` on every command, so it can never flush everything; to remove one user use `OWNERS FORGET`. Inside a transaction the owner named by `MULTI`, or by any queued command, decides the case. Watches, tracking and notifications follow the scope of the deletion: a flush of one user's keys marks only that user's watchers and invalidates only the clients pinned to a scope that dominates it. Only the flush that deletes everything stops a running snapshot and, when save points are configured, saves at once; a flush of one user's keys or of the shared keys does neither, so a snapshot that is being written goes on with the keys it holds.

## Vector sets

A vector set element carries its writer's scope, and each label and owner present in a set is its own partition of the set. A user's partition starts as a flat block that is searched exactly and becomes a graph above 512 elements, as label partitions do. A set has a key in every partition, owner or shared, where it holds elements, and a reader sees the set exactly when it can see one of its elements; `DEL`, `UNLINK`, expiry, eviction, `RENAME` and `MOVE` act on the elements of the command's own scope only.

Elements resolve with the same order as keys: the user's own element at exactly the reader's label, then the shared element at exactly that label, then the highest visible rank with the user's own element first at equal rank. `VSIM` searches every visible partition and merges exactly by score, then by name; `VCARD`, `VRANGE`, `VRANDMEMBER`, `VINFO` and `VLINKS` count and list each visible name once. A write of an element the writer sees only at another of its labels, or only as shared, answers `INUSE element in use at <label> SHARED` or `... OWNER <id>`, and `LABEL OF <key> <element>` carries the same suffix. Every partition of a set, a user's or a shared one, is charged a figure computed from its own content by the formula that [Vector sets](vector-sets.md) gives, so a user's charge never moves with other users' partitions, with hidden labels or with a restart; the set's shared structure, its owner index and its name indexes count as global memory only. Opening a user's view costs the visible shared partitions, the user's own partitions and, when a collision check is due, the user's own names, never anything per other user.

## Search indexes

An index definition is shared or private to its owner. Each hash or JSON key contributes to visible definitions from its own scope. A query uses the visible shared partitions and the caller's own partitions, with the usual key precedence for names they share. A hidden definition produces the same response as a missing one. Dropping a shared definition with `DD` removes indexed keys at the command's exact scope. `OWNERS FORGET` also removes the owner's definitions and indexed partitions. Each definition and partition charges its own scope by content. A fixed `owner:<id>` login can use a pooled client without wrapping each search or write. ## Quotas and memory

`OWNERS QUOTA <id> LIMIT <bytes>` sets one user's quota, and `owner-quota-default` applies to every user without one; 0 means no quota. The quota is checked before every command that can grow memory, the commands with the `denyoom` flag: when the user's use is already above its quota, Eski expires all due keys and hash fields in that user's own partitions across databases, using the command's clock. If the user is still over, Eski evicts inside those partitions by `maxmemory-policy` (nothing under the default `noeviction`). If the user is still over after that, the command answers `OOM command not allowed when used memory > 'owner-quota'.`. The check compares the use so far and, unlike `maxmemory`, does not count the arriving command's own arguments, so the key write that crosses the limit is accepted and the next growing command is the one refused; reads, deletions and other commands without `denyoom` are never refused for the quota. A script load is checked with its own size included, as described below. Quota eviction samples from the user's keys by label, database and key name, independent of the current layout of the key tables. Policies that rank candidates use up to `maxmemory-samples` keys per partition.

A user's quota use is what `OWNERS INFO` and `OWNERS QUOTA` report as its bytes and what `OWNERS FORGET` returns. It is the memory the server holds for that user alone, summed over every database and every label of the user:

| Counted in the user's quota use | Not counted |
| --- | --- |
| keys and values with their type structures, and for each of the user's vector set partitions the figure the vector set formula computes from its content: the set's header, owner index and tables as if the partition were the whole set, its elements with names and attributes, the room it has grown to, its graph, an allowance for its names in the set's index and for the user's record in the set | the user's places in the server's shared lists of partitions with work due and in the eviction sampler, 8 bytes each; these count as global memory, so a user's figure moves neither with other users' data nor when the server's background work does |
| the records and key tables of the user's partitions, the record that keeps its `SCAN` cursor space, its random streams and its registries of names held at several labels | the memory of the connections that act for the user: query and output buffers, queued transaction commands, watched and blocked keys, subscriptions and tracking entries, bounded by the client limits and `maxmemory-clients` as without owners |
| the owner entry: the entry, the id text and its slot in the owner table | contexts, cached signed tokens and slow log entries |
| the scripts the user's scopes hold in the script cache | the Lua engine memory a running script uses, bounded over the whole engine by `lua-max-memory` |
| | shared data written on the user's behalf with `SHARED`, which label quotas count |
| | the allocator's own per-block overhead, about 0.1 KiB per user, which `used_memory` does not count either |

A user's quota use depends only on the user's own data and the user's own commands. Every hash, list, set, sorted set and stream is charged the size computed from its content, the same figure `MEMORY USAGE` reports to the user: every allocation at the size a fresh block of its length takes (the length plus 8, rounded up to 16, minus 8, at least 24), a table at the capacity a load gives its count, a sorted set's elements at the average height of its list, a stream's index at 10 bytes for each id and 40 bytes plus the length for each name, and a stream's last node at the room a server opens a node with, 4,096 bytes or `stream-node-max-bytes` when that is smaller. The charge is kept up to date as each write runs, so no write walks the key to charge it; to keep it, a stream on a server with a label scheme or owner mode holds 16 bytes more than on one without, which its figure, `used_memory` and `MEMORY USAGE` count. A string is charged its key, its value and the room the user's own `APPEND` and `SETRANGE` gave it, a vector set by its formula. Each partition's key table is charged as the table a partition built for its current keys would have: 34 bytes for one key, 52 for two, 88 for three or four, 352 up to fourteen keys, and above that a table of 16 slots doubled until the keys fill at most seven eighths of it, at 18 bytes a slot plus one control byte a slot rounded up to 64, and rounded up to whole 4 KiB pages above 1,024 slots, never the table the partition holds while it grows, shrinks or is migrated in the background; `owner-compact no` charges the 352-byte table from the first key. Quota decisions use the user's data and the command's clock. The allocator's choices, other users' data and commands, and the pace of background expiry cannot change the decision. Two parts of the figure follow the user's own history and can read differently after a restart: a string's room, which a load gives back as the exact length, and the records listed under [What stays observable](#what-stays-observable). The figures in the top-only `OWNERS INFO` and `OWNERS QUOTA` reports include expired data until it is removed. `used_memory`, `maxmemory` and its eviction, and `MEMORY USAGE` for a caller that acts for no user count what the process really holds. `DEBUG CHARGE-CHECK`, at a top label with `enable-debug-command`, recomputes every key's charge from its content and every partition's heap figure from its keys, compares them with the running figures and answers the number of keys it checked, or an error naming the first difference.

A vector set partition is charged at least what its own memory and the set's header hold, so a set that several users or labels share has its header charged to each partition and the charges add up to more than the set holds; `used_memory` counts the real amount. One part of a set is not bounded by the charge: the name index, where each element is charged an allowance of 40 bytes plus its name and the index can hold more (see [Vector sets](vector-sets.md)). The set's table of users follows the partitions users hold in it: when users leave, it gives back its room and keeps at most two entries of 12 bytes for every user partition still in the set, and never fewer than four, which the charges of the partitions present cover, since each of them is charged the set's header with its smallest tables. To shrink it, Eski may give a user's partition a new place in the table while other users leave; replies, charges and files do not show it. The charge of a partition does not fall back when elements are removed from it: the removed elements' names and attributes leave it, but the room its vector area and tables grew to stays allocated and stays charged. A graph's tables leave the charge when the partition shrinks to 128 elements, and the rest returns only when the partition itself goes, with its last element or when the key is deleted, expires or is evicted for that user at that label; a user at its quota makes room by removing keys, not elements.

The quota sums all of the user's labels, so the user's own data at a higher label can make a write at a lower label refuse, or evict the user's keys there: a channel between labels within one user, which this release does not close. Label quotas count shared data only, so one user's writes never evict another user's keys through a label quota. Global `maxmemory` still covers the whole server: its eviction picks keys of any user and its refusals answer whichever command comes next, so without a quota for every user it remains a channel between users, as it is between labels. `owner-partitions-max`, when set, caps the number of owner partitions and answers `ERR owner partition limit reached` past it; that count is itself a channel between users.

A user's scripts count too. Every script a user's scope holds in the script cache, loaded with `SCRIPT LOAD` or `EVAL` at any label, adds its source and its cache record to the user's quota use and to the `bytes` of `OWNERS INFO`, also when the source was already cached for another scope, so the charge does not tell the two apart. A `SCRIPT LOAD` or `EVAL` that would take the user over its quota first expires the user's own due keys and hash fields when expiry is allowed. A write pause also pauses this expiry. If the source still needs room, Eski drops enough of that scope's least recently used `EVAL` entries to fit, when possible. Pinned `SCRIPT LOAD` entries and entries from other scopes remain in the cache. If the eligible entries cannot make enough room, Eski keeps them and answers `OOM command not allowed when used memory > 'owner-quota'.` before the source is stored or compiled. Running a script the scope already holds, by `EVALSHA` or by `EVAL` of the same body, is never refused for the quota. Script bytes also count when a key write checks the quota, so a user over its quota with scripts alone is refused key writes after its keys are evicted. The bytes leave the user's use when an entry is evicted, at `SCRIPT FLUSH` and at `OWNERS FORGET`, whose `bytes` include them. They count once in `used_memory`, as script cache memory. Scripts loaded as `SHARED` or at a label without a user stay outside quotas.

Every owner structure counts in `used_memory`, whether it counts in a quota or as global memory. Measured on this release with 300,000 users, a user holding one small key costs 802 bytes in `used_memory` and 890 bytes of resident memory. A user holding one small key and one 128-dimension Q8 element in a vector set that all of them share, beside a shared graph of 50,000 elements in the same set, costs 1,516 bytes counted and 1,652 resident, of which about 1.4 KiB counts in its quota use, so 300,000 such users take about 455 MB counted and 496 MB resident; `python3 -I bench/owners/scale.py --size full` repeats that measurement and checks every user's isolation while it loads. An owner entry, about 0.2 KiB (211 bytes for a 7-byte id), is created by the first command that names the id, reads included, and lasts until `OWNERS FORGET`; it counts in the user's quota use.

A partition starts small and grows with its keys. Its record holds only what an owner partition uses, 376 bytes. Its first key table holds one key and is replaced by tables for two and then four keys, and the fifth key brings the ordinary 16-slot table, about 0.3 KiB more. After a command that leaves keys only in the first two slots of a 16-slot table, the table shrinks back to four slots. The structures that schedule hash, set and sorted set maintenance, 152 bytes, are allocated with the partition's first such key and kept until the partition is released. Every table step keeps each key in the slot it had, so these shapes change memory figures only: replies, `SCAN` cursors, `KEYS` order and random draws are the same as in the fixed form that `owner-compact no` selects. A released partition returns all of its bytes to the user's quota use.

Search index definitions carry the creating command’s owner. A definition-only owner appears in the top-only `OWNERS LIST` reply. The keys, elements and partitions in `OWNERS INFO` still reflect the user’s stored data. Definition bytes are outside owner accounting in this build. Forgetting an owner also removes that owner’s definitions.

## Forget

`OWNERS FORGET <id>` runs at once on the coordinator, freeing large values lazily. It removes every key and vector set element of the user in every database, sends the `del` events at the user's scope when keyspace notifications are on, marks the user's watchers, invalidates its tracked keys, closes the connections pinned to it, bound to it or blocked as it, and drops its contexts, cached tokens, slow log entries, random streams and entry. It reads and changes no shared partition and no other user's structure, so nothing another user or a shared reader can observe changes, apart from global memory and timing. It replies with the `keys`, `elements` and `bytes` removed; `bytes` includes the entry. Shared data written on a user's behalf is not that user's data and stays.

## Contexts and signed tokens

`CONTEXT CREATE [LEVEL <marking>] [TRUST <trust>] [OWNER <id> | SHARED]` fixes a label and an owner. The owner defaults to the creating command's owner and must be one the login may act for, else `ERR invalid owner`. `CONTEXT INFO` also returns the `owner` (the id, or nil for `SHARED`) in owner mode. An agent that holds a handle cannot change its owner, and the contexts of a forgotten owner are dropped.

A signed statement may carry one line `owner <id>` or one line `shared`. On an `owners:*` login exactly one of them is required; on other logins a token without one runs at the login's own owner. The token's owner must be one the login may act for, and when the token names a context the context must have the same owner. Servers without owner mode refuse such tokens, because they refuse unknown lines.

## Transactions and scripts

`MULTI` binds the label and the owner. A queued command that names another owner is refused when it is queued with `ERR the command's owner differs from the transaction's owner`, and `EXEC` must carry the same owner or none, else it answers `EXECABORT Transaction discarded because of: the command's owner differs from the transaction's owner`. `WATCH` records its scope: when any key was watched at a scope other than the transaction's label and owner, `EXEC` runs nothing, whatever the data, and answers `EXECABORT Transaction discarded because of: the command's label differs from the transaction's label` when a label differs and `EXECABORT Transaction discarded because of: the command's owner differs from the transaction's owner` when only owners differ. A label that differs is reported first, as labels report it without owners.

Scripts and functions run for the caller's owner, and `LABEL WHOAMI` inside them shows it. `LABEL AS` stays refused inside scripts, and `OWNERS` is not allowed from scripts. While a script is busy, `SCRIPT KILL`, `FUNCTION KILL` and the running script in `FUNCTION STATS` need a label that dominates the script's label and, on top of that, the script's own owner or the operator scope. Seeing the script's owner is not enough: `SHARED` sits below every user, yet a user may not act on a script that runs as `SHARED`, nor on one that runs for another user; for such a caller `FUNCTION STATS` shows no running script and the kill commands answer `ERR this command needs a label that dominates the running script's label`.

The script cache and the stored functions follow the scope as they follow the label in [Labels](labels.md#transactions-and-scripts). Changing stored functions and `SCRIPT FLUSH` need the operator at top. A cached script is visible to a caller that sees one of the scopes that loaded it: a user sees the scripts loaded as `SHARED` at labels it dominates and its own, never another user's, and the operator at top sees them all. The `EVAL` bound and its eviction apply per scope, each scope has its own `math.random` stream, every run starts with the engine's starting cjson settings, and `OWNERS FORGET` drops the scripts and the stream of the forgotten user. Function code is installed by the operator and must not keep data between calls, because a library's closures survive calls for every user. [Scripts](scripting.md#labels-and-owners) gives the details.

## The push pin

`SUBSCRIBE`, `PSUBSCRIBE`, `SSUBSCRIBE` and `CLIENT TRACKING ON` fix the connection's owner together with its label. A login without an owner rule pins at `SHARED`, an `owner:<id>` login at its id, and an `owners:*` login must name the owner on that command with the owner-only prefix, as in `LABEL AS OWNER u42 SUBSCRIBE ch`; a marking in the prefix stays refused as labels refuse it without a session. An `owners:*` operator that names no owner pins at every owner. The pin is set only after the command passes the arity and `ACL` checks and the label and owner refusals, so a push command refused with `NOPERM`, or with an owner refusal such as `ERR this login must name an owner with every command`, pins neither the session nor the owner. After pinning the connection receives only messages whose scope its pin dominates, and every later command on it that names another owner is refused with `ERR this connection is bound to another owner`, so a client-side cache never mixes two users. `RESET` and `AUTH` to another login clear the pin; a connection that still holds subscriptions or tracking is then pinned at the new login's owner, or closed when the new login must name owners. `LABEL WHOAMI` shows the pin in `pinned-owner`: nil, `SHARED`, `OWNER <id>` or `EVERY`.

## The operator and top

Top in owner mode means two things at once: the command's label dominates the scheme's top label, and the login carries `owner-operator`. The top-only commands of labels (`MONITOR`, `LATENCY`, `SWAPDB`, `DEBUG`, `CLIENT PAUSE` and `UNPAUSE`, `MEMORY STATS`, `DOCTOR`, `MALLOC-STATS` and `PURGE`, `SLOWLOG RESET`, `CONFIG SET`, `CONFIG REWRITE` and `CONFIG RESETSTAT`, `LABEL COPIES` and `LABEL QUOTA`, `FUNCTION LOAD`, `DELETE`, `FLUSH` and `RESTORE` and `SCRIPT FLUSH`, and the persistence commands that [Labels](labels.md#what-is-enforced-in-this-release) lists), the full `INFO` numbers and the `OWNERS` subcommands other than `HELP` need it, else `ERR this command needs a label that dominates the whole label scheme`, or `ERR this command needs a login with the owner-operator right` when the label is top and only the operator scope is missing, as it always is for a login without `owner-operator` in owner mode without a label scheme. For the filtered introspection below, the operator sees every owner at the labels it dominates. `CLIENT PAUSE WRITE` judges an owner-prefixed command by the command it wraps, so a login that must name an owner with every command still has its writes held, and the held command names no owner before it runs; the [labels rule](labels.md#what-is-enforced-in-this-release) gives the details.

## Server-wide channels

| Channel | Rule in owner mode |
| --- | --- |
| Pub/sub | a message carries the publishing command's scope and reaches only connections whose pin dominates it; `PUBLISH` and `SPUBLISH` count the receivers at exactly the publisher's scope; `PUBSUB CHANNELS`, `NUMSUB`, `NUMPAT`, `SHARDCHANNELS` and `SHARDNUMSUB` count only the subscribers the caller dominates |
| Keyspace notifications | carry the changed copy's scope, its label and its owner, expired and evicted events included, so they reach only pins that dominate it: a user's events reach that user's pins and operator pins, shared events reach every pin at a dominating label |
| `WATCH` | aborted by any write at a scope the watcher's own scope sees, shared writes included, and never by another user's writes; flushes and `SWAPDB` mark watchers by what their own view held |
| Blocking | pops and moves wait on the name at exactly their label and owner; read-only blockers such as `XREAD` wake on writes at any scope they see |
| Client tracking | invalidations, broadcast mode, flushes and `REDIRECT` targets included, reach only connections whose pin dominates the written scope, so a client-side cache never mixes two users |
| `MONITOR` | top in owner mode, so operator only, and sees every command |
| `CLIENT LIST`, `CLIENT KILL`, `CLIENT UNBLOCK` | a connection's scope is its pin; for a login without an owner rule it is `SHARED`, for an unpinned `owner:<id>` connection its id, and for an unpinned `owners:*` connection, which serves many users in turn, every owner, which only the operator sees; a connection always sees itself |
| `SLOWLOG GET` and `LEN` | an entry carries its command's scope and shows to the callers that dominate it; ids and the capacity stay shared |
| `INFO` | below top as in labelled mode, with `INFO keyspace` counting the caller's view; the operator also gets an `# Owners` section with `owners_known` (entries in the owner table), `owners_holding_data` (users with a key or element), `owner_partitions` and `owner_bytes` (users' data and structures, entries included); at operator top `DBSIZE` and `INFO keyspace` count the shared view |
| Scripts and functions | run at the caller's scope; the script cache, `SCRIPT EXISTS` and `EVALSHA` see only scripts loaded at scopes the caller sees; stored functions change only at operator top, and `FUNCTION LIST` shows the operator's libraries to everyone |
| `ACL LOG` | stays an administrative command |

## The OWNERS command

| Command | Rule |
| --- | --- |
| `OWNERS FORGET <id>` | removes every key and vector set element of the owner in every database, closes every connection pinned to the owner, bound to it by `MULTI` or `WATCH`, or blocked as that owner, drops its contexts, its cached tokens and its slow log entries, drops its id and writes an `owner-forget` audit record with the counts; replies with a map of the `keys`, `elements` and `bytes` removed (see [Forget](#forget)) |
| `OWNERS INFO <id>` | the owner's `keys`, `elements`, `bytes`, `partitions`, `labels` and `quota`, counts only |
| `OWNERS LIST <cursor> [COUNT <count>]` | a cursor over the ids of the owners that hold data (a key or a vector set element in any database), in order of first use; each step costs the same whatever the owners hold |
| `OWNERS QUOTA <id> [LIMIT <bytes>]` | shows the owner's quota and used bytes, or sets the quota (0 falls back to `owner-quota-default`) and writes an `owner-quota` audit record |
| `OWNERS HELP` | the subcommands |

`FORGET`, `INFO`, `LIST` and `QUOTA` are the subcommands `owners|forget`, `owners|info`, `owners|list` and `owners|quota`, in the `@admin` and `@dangerous` categories only, and need the operator at top. Shared data written on a user's behalf is not that user's data and is not forgotten.

## Audit

The audit file of labels receives `owners-on` when owner mode turns on, `owner-forget` with the id and the counts, `owner-quota` with the id and the limit, and the ACL changes to owner rules through `acl-setuser`. Records never carry values.

## Persistence and forgetting

A snapshot of an owner-mode server holds every user's data at its labels and every shared copy, the age order of copies of one name within each user and within the shared data, the label quotas and the owner quotas. It lists each owner that holds a key or has a quota; an owner entry that holds neither is not saved and is created again on first use. A restart loads the users back by their ids, `DEBUG RELOAD` loads them into the owner table it already has, so a pinned connection, a transaction, a watch, a context or a slow log entry keeps meaning the same user, and a file holds exactly one mode: a snapshot written in owner mode loads only on a server in owner mode with the same label scheme, and a label-only snapshot never loads in owner mode. Keys that expired while the server was down are dropped at load and leave no partition and no owner entry behind. A vector set is saved one partition at a time, a user's partition in that user's own partition of the file, whether it is still a small flat block or has become a graph, so after a restart each user reads the same replies from every vector command, and a user whose set key expired during the downtime leaves nothing in the set that another user or a shared reader could notice. `DUMP` of a vector set returns the caller's own view, and `RESTORE` builds the set in the caller's own scope; a payload whose reservation alone is larger than the caller's quota is refused with the reply that a write over the quota gets. [Persistence](persistence.md#labels-and-owners) describes the file and its checks.

`OWNERS FORGET` adds a `sequence` field to its reply: every forget, also of an id that was never seen, takes the next number of one server-wide sequence, and the snapshot records the number it covers. `INFO persistence` at operator top shows `owners_forget_sequence`, the last number given, `owners_forget_in_snapshot`, the number covered by the last successful snapshot, and `owners_forget_in_aof`, the number covered by the last append-only rewrite that started after it, once the files from before that rewrite are gone; while the append-only file is off it equals the sequence only when no file of an earlier log is left in the log directory. While no save points are configured and the server has neither written nor loaded a snapshot, `owners_forget_in_snapshot` equals the sequence only when no file of the `dbfilename` name is in `dir`; such a file, which this server neither read nor wrote, keeps the field at its last value, and a warning at the forget and when `owners-forget-snapshot-delay` has passed names it, for the operator to delete or to replace with `SAVE`. A forget has reached the snapshot when `owners_forget_in_snapshot` is at least its number. Eski writes that snapshot itself: a background save starts `owners-forget-snapshot-delay` seconds after a forget (hidden, default 300; several forgets within the delay share one save), and the setting at 0 leaves it to the operator, who runs `BGSAVE` and reads the field. A clean shutdown, by `SHUTDOWN` or by a signal, saves a snapshot while a forget is not yet in it and snapshots are in use (save points configured, or a snapshot written or loaded since the start), also without save points and whatever the delay says, so that a restart cannot bring the forgotten data back; if that save fails the shutdown is refused as for any failed final save. `SHUTDOWN NOSAVE` and the `nosave` shutdown settings skip the save as asked, and the server then logs a warning that the data file still holds the data the forget removed. Older snapshots, copies, backups, files moved away and the audit file, whose `owner-forget` record carries the id, are the operator's to delete; at startup Eski removes temporary snapshot and rewrite files that a crash left in its directory. The append-only file is covered the same way, by a rewrite instead of a save: `owners-forget-aof-delay` seconds after a forget (hidden, default 300, 0 for the operator to run `BGREWRITEAOF`) Eski starts a rewrite, the history files that held the user's records are deleted when a rewrite that started after the forget finishes, whatever `aof-disable-auto-gc` says, and `owners_forget_in_aof` moves to the forget's number once they are gone, so that no file in the log directory has the id or the data (a forget that happens while a rewrite runs waits for the next one). A clean shutdown rewrites the log first when a forget is not yet in it, `SHUTDOWN NOSAVE` skips that with a warning, and a start from a log whose last forget no rewrite covered schedules the rewrite again. Files outside the log directory stay with the operator, as above. See [Persistence](persistence.md#the-append-only-file) for the records.

## What stays observable

Everything that [Labels](labels.md#what-comes-next) lists as observable across labels stays observable across users, among them the `BUSY` replies that every connection gets while any user's script runs, counts that include expired keys not yet removed at a pace all users share, the label table that one login can fill for everyone, and the shared Lua engine state with the closures of stored functions. Owner mode adds these, which are documented limits of the guarantees, not settings:

- Timing is outside the claims. How long a command takes can depend on what other users hold, for example through the allocator, eviction and the size of shared structures.
- Global `maxmemory` eviction crosses users. Without a quota for every user, eviction under `maxmemory` picks keys of any user, and its refusals answer whichever command comes next (see [Quotas and memory](#quotas-and-memory)).
- The owner quota spans all of a user's labels, so the user's own data at a higher label can refuse a write, or evict the user's keys, at a lower label.
- A user that deleted everything keeps a small record. The record of its `SCAN` cursor space, 128 bytes for each database it wrote in, stays until `OWNERS FORGET` (see [Keys](#keys)). A restart rebuilds these records only where the user holds data, so after a restart a user that emptied a label or a database, or whose keys there expired while the server was down, reads that many bytes lower in `OWNERS INFO`. The same holds for the record of a scope's random stream, which a user's draws at a label create (`RANDOMKEY`, `SRANDMEMBER`, `SPOP` and the level of a `VADD`, reads included): 64 bytes for each such label after the first and 104 more with the second, kept until `OWNERS FORGET` and not rebuilt by a load.
- `owner-partitions-max`, when set, is one count for all users.
- The disk is shared like memory: a snapshot and the append-only file hold every user's data, so their sizes, the time a save or a rewrite takes and a failed save or write depend on other users' data, and after a failed background save `stop-writes-on-bgsave-error` makes every user's writes answer `MISCONF`.

Reads for another user leave no trace, so shared data that users only read looks unused to the eviction policy; where that matters, use per-user and per-label quotas or the `noeviction` policy.

## What this release does not do

`DUMP` serialises the copy the caller reads and `RESTORE` writes it at the command's own scope, so moving one user's data to another server goes through a client that reads with that user's `LABEL AS OWNER` head and writes with it. Owner commands run on the coordinator, as every command does with labels on. Function libraries stay global: the operator installs them and every user calls the same code. Per-user retention and sharing private data between users are not built.

Verify with `python3 -I test/compatibility/owners_keyspace.py --server bin/eski`, `python3 -I test/compatibility/owners_subjects.py --server bin/eski`, `python3 -I test/compatibility/owners_compact.py --server bin/eski` and `python3 -I test/compatibility/owners_persistence.py --server bin/eski`, each also with `--keyspace-threads 2`, `odin test src/owner`, `python3 -I proofs/verify.py --project label` and the owner modes of the [labelled-mode gate](build-run-test.md#labelled-mode-gate). `python3 -I bench/owners/scale.py` loads many users beside a shared vector graph, checks that each sees its own data and the shared data and nothing of its neighbour's, and reports bytes per user; the [speed-pass harness](build-run-test.md#speed-pass-harness) describes it with the other tools of the pass.
