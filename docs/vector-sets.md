# Vector sets

A vector set maps binary-safe element names to vectors and indexes them in an HNSW graph for similarity search. `VADD` adds an element or replaces its vector, `VREM` removes one, `VSETATTR` and `VGETATTR` manage a JSON attribute per element, and `VSIM` returns the elements closest to a vector or to another element. `VCARD`, `VDIM`, `VEMB`, `VLINKS`, `VINFO`, `VISMEMBER`, `VRANDMEMBER` and `VRANGE` inspect a set. The first successful `VADD` creates the key and removing the last element deletes it; any of these commands answers `WRONGTYPE` for a key of another type.

```sh
redis-cli -p 6399 VADD demo:docs VALUES 3 0.1 0.9 0.2 intro SETATTR '{"year":2024}'
redis-cli -p 6399 VADD demo:docs VALUES 3 0.8 0.1 0.3 setup SETATTR '{"year":2026}'
redis-cli -p 6399 VSIM demo:docs VALUES 3 0.1 0.8 0.3 WITHSCORES COUNT 5 FILTER '.year > 2025'
```

Vectors arrive as `VALUES n x1 ... xn` or as a little-endian float32 blob after `FP32`. They are normalised and stored as signed 8-bit codes by default, as float32 with `NOQUANT` or as one bit per component with `BIN`. The quantisation, the link count `M` and a `REDUCE` projection are fixed when the set is created, and every later `VADD` must repeat them when they differ from the defaults. Scores run from 0 for opposite directions to 1 for the same direction. `VSIM` returns ten elements unless `COUNT` says otherwise, searches with an exploration factor of 100 unless `EF` says otherwise, keeps scores of at least one minus `EPSILON`, and with `TRUTH` scans every element and orders equal scores by insertion. `FILTER` takes an expression over the attribute's top-level fields; elements without an attribute never match. With `compute-threads` above 0, `VSIM` searches on a compute worker and `VADD` with `CAS` searches its neighbours on a worker and is committed on the coordinator as the `VADD` it is when the search has finished; a client pause that covers writes holds that commit until the pause ends. A search stays on the coordinator when it says `NOTHREAD`, when `vset-force-single-threaded-execution` is `yes`, when `compute-threads` is 0 (the default, where nothing is different from a server without workers), inside a transaction, a script or a function, for a connection with client tracking, and when the caller can see fewer than 64 elements of the set. The caller's own view decides that last case, so a reader cannot tell from the choice, or from any reply, what data it may not see. When the worker queue or `compute-max-memory` is full, while the pool is stopped for a fork or while the server loads, the coordinator searches at once and answers or commits at the point a worker's result would have been taken, so no client can tell from its replies how busy the pool is. The reply has exactly the bytes the coordinator would have produced at the same point of the command order, and a write to a set waits for the searches that are reading it. [Threading](threading.md#vector-search-on-compute-workers) has the rules, the lifecycle and the checks.

`REDUCE` projects every input onto a fixed pattern of Hadamard signs. The projection preserves vector lengths exactly only when the reduced dimension is at most the largest power of two that divides the input dimension; other shapes are accepted, as the reference accepts them, but their rows are not orthogonal.

`TYPE` reports `vectorset` and `OBJECT ENCODING` reports `raw`. `MEMORY USAGE` is exact, the dataset counts in `used_memory`, eviction policies select vector sets like other keys and `VADD` is refused with an out-of-memory error above `maxmemory`. With a label scheme or owner mode, `MEMORY USAGE` from a caller below top counts only the partitions the caller can see, and computes each from its own content by a fixed formula instead of the allocator's sizes, because those sizes shift with what other labels and owners allocated before and a reply must not move with activity the caller cannot see. Label and owner quotas charge every partition the same figure, so the reply of a caller that sees one partition is that partition's charge. Every partition counts the set's own header and tables as if it were the whole set: 808 bytes for a shared partition and 1,016 for a user's, which adds the set's owner index. With them a shared partition counts 1,424 bytes before its elements, a user's graph partition 1,796 and a user's small flat partition 1,428, the user's figures including 180 bytes for the user's record in the set. A set with several partitions is therefore charged its header once for each. Every element counts its name and its stored attribute, each rounded like a heap block (the length plus 8, rounded up to 16, minus 8, at least 24) plus 16 bytes, and 40 bytes plus the name's length for its entry in the set's name index. The partition then counts the room it has grown to, C slots, which only its own writes enlarge and which a restart keeps: the vector area (C times the stored vector size rounded up to 4 bytes, plus 4 bytes per slot for the norm and 4 more for int8, where the stored vector takes the dimension in bytes for int8, 4 bytes per component with `NOQUANT` and the dimension rounded up to a multiple of 64 bits with `BIN`) rounded like a heap block plus 32 bytes, and the element and order tables of 40 and 4 bytes per slot, sized for one growth step beyond C (twice C below 16 slots, one and a half times C below 64, one and a quarter times C above), each rounded plus 16. A partition that holds a graph (one that has grown past 512 elements and not yet shrunk to 128, or a set that existed before the scheme) with room for G nodes adds its link table, G times 2M links plus 8 bytes rounded plus 32; three tables of 2, 1 and 4 bytes per node, each rounded plus 16; the upper-layer lists, one and a half times the room they may take but at least 256 links, where that room is the larger of one and a quarter times M + 1 links for every upper layer of its elements and G times M + 1 links over 3, plus 8 bytes, rounded plus 16; and 4 bytes per node, rounded plus 16, once duplicate vectors are linked; a link takes 2 bytes up to 65,535 nodes, 3 up to 16,777,215 and 4 above. A heap block of 128 KiB or more is rounded up to whole 4 KiB pages instead. With a label scheme or owner mode a partition's upper-layer lists never take more than that room: when a write leaves them above it, because replaced or removed elements freed lists that no new element reused, Eski packs the lists together and releases the rest. Packing moves lists and changes no link, so search results and `VLINKS` replies stay as they were, and a set on a server without labels or owners is never packed. If the smaller block cannot be allocated, the lists stay as they were and the partition holds more than that room, and more than its charge counts for them, until a later write to it packs them. The formula is therefore at least what the partition's own blocks and the set's header hold, whatever its writer does, so it reads above the exact figure that a top caller, and every caller of a server without labels or owners, still gets; `used_memory` counts the exact figure. The name index is the exception: its 40 bytes plus the name's length per element is an allowance, and the index, which all partitions of a set share, can hold more: names longer than about 50 bytes take more than the allowance as soon as they are inserted, up to twice the allowance for names near 1,000 bytes (about 3 percent of a set's charge with 4,000 random names of 120 bytes), and the index holds up to about three times the allowance after most names of a set were added and removed again, because it keeps its pages at least a quarter full instead of repacking them. A partition's figure does not fall back when elements are removed, because the room its vector area and tables grew to stays allocated: the graph's tables leave it when the partition shrinks to 128 elements, the rest when the partition's last element goes or the key is removed at that label. Expiry, `DEL`, `UNLINK`, lazy freeing, `RENAME`, `MOVE`, `SWAPDB`, `DUMP`, `RESTORE`, `SCAN ... TYPE vectorset` and the flush commands work as for other types. `COPY` answers `ERR not supported for this module key` and `SORT` answers `WRONGTYPE`. The vector commands publish no keyspace events of their own; key creation and read misses publish `new` and `keymiss` as for every type, and writes invalidate `WATCH` and client tracking as soon as they reach the key, whatever their outcome.

Snapshots store a vector set as a module-type value named `eski-vset` with encoding version 2, holding Eski's own encoding of the set's exact state: every element with its slot, insertion sequence, stored vector, norm, int8 range and attribute, every graph slot with its level and its neighbour lists in their order, the chains that link duplicate vectors, the free slots in the order they will be reused, the level generator's state and the node counter. A set reloaded from a snapshot, from `RESTORE` of a `DUMP` payload or from a rewritten append-only file therefore answers every query exactly as before, including the order of equal scores and the members kept when `COUNT` cuts a tie, and later writes build the same graph they would have built without the restart. Payloads of encoding version 1, written by earlier builds, still load; they carry no graph, so the graph is rebuilt, and they are held to the same limits as version 2 (an M of at most 4,096, distinct insertion sequences and a node counter below 2^63), so that whatever loads can be written and read back. The loader treats a payload as untrusted and refuses it before using it when a count, a slot, a sequence, the free list, a level, a neighbour list, the entry point or a chain of duplicates is inconsistent, when a link has no reverse link, or when the payload would make it reserve far more memory than its own size justifies. The reserved size follows a fixed formula that belongs to the format and does not move with the server's in-memory records: the arena capacity times the stored vector size plus 64 bytes per slot, plus 16 bytes per element, and for a payload that carries a graph also the graph capacity times 2M links of the payload's link width plus 64 bytes per slot, plus the upper-layer lists (their count times M + 1 links, one and a half times over), plus 256 links and 30 times M + 1 links of slack. A payload is admitted when that size is at most 64 times its length plus the same figure for 16 slots. Because free slots keep their place, a set that has shrunk keeps the footprint of its largest size after a reload, and the writer appends zero bytes to the payload of such a set, enough to stay within half of what the reader admits, so that every set the server holds can be saved and loaded again and a later build with larger records still admits older files. The node counter must stay below 2^63: a payload at the edge loads, and a write that would pass the edge answers an out-of-memory error instead. The payload must be stored as a plain string inside the module value; a compressed or integer-encoded string is refused. Beyond that, `RESTORE` of a vector set is admitted like any other write, and only a payload whose header agrees with its length but whose reservation alone exceeds `maxmemory`, or the caller's owner quota, is refused before anything is allocated, with the reply that a write over that limit gets. A refused snapshot stops the load with the reason, and `RESTORE` of any other malformed payload answers `ERR Bad data format`. With a label scheme or owner mode a snapshot stores each partition of a set separately, each with its own graph, free slots and level generator state, and `DUMP` returns the caller's view as a flat payload of version 2 that carries no graph; `RESTORE` refuses the per-partition payloads that only snapshots hold ([Persistence](persistence.md#labels-and-owners) describes both). `DUMP` payloads use the same framing, so the reference and Eski each refuse the other's payloads and snapshot files cleanly. The append-only file receives `VADD`, `VREM` and `VSETATTR` as written whenever they change the set, including a `VADD` that replaces an existing vector, which the reference neither logs nor counts as a change. A rewrite without the RDB preamble writes each vector set as `RESTORE` of its version 2 payload followed by `PEXPIREAT` when it expires, so the rewritten file reloads the same graph; `VADD` commands would rebuild a different one, and the reference fails such a rewrite. Eski draws one random seed for the dataset when the first vector set is created and derives the level generator of every new set from it and from the key, so clients cannot predict the levels of a graph, and the same commands run on two fresh servers build different graphs. The hidden startup setting `label-stream-seed` exists for tests: when it is not zero, with labels on or off, the dataset seed is derived from it instead of drawn at random, so two servers started with the same value and given the same commands build the same graphs; a seed loaded from a persistence file still takes precedence over it. Snapshots carry the dataset seed, so sets created after a restart derive their levels from the same seed as before it.

The commands carry upper-case names, the `module` flag and the `module` group, as on the reference. Unlike the reference, which leaves them outside every ACL category and declares every key read-write, Eski gives them the ordinary categories and key flags, because logins are built by category and a login meant to be read-only must not be able to write: `VCARD`, `VDIM`, `VEMB`, `VGETATTR`, `VINFO` and `VLINKS` are `@read` and `@fast`, `VISMEMBER`, `VRANDMEMBER`, `VRANGE` and `VSIM` are `@read` and `@slow`, `VSETATTR` is `@write` and `@fast`, and `VADD` and `VREM` are `@write` and `@slow`, with `@fast` given exactly to the commands that carry the `fast` flag, as for every other type. The ten read commands declare their key `RO access`, so a login with read-only key rights such as `%R~*` runs them, and the three write commands keep `RW access update`. So `+@read` grants the read commands and no write command, `+@all -@write` denies `VADD`, `VREM` and `VSETATTR`, `ACL CAT`, `COMMAND LIST FILTERBY ACLCAT`, `COMMAND INFO` and `COMMAND GETKEYSANDFLAGS` show the categories and key flags, and rules by name such as `+vadd` or `-vsim` work as before. There is no vector set category. `MODULE LIST` reports one entry named `vectorset` with version 1 so that clients can detect the commands, while `HELLO` and the `INFO` module section stay empty and `MODULE LOAD` always fails. `CONFIG SET vset-force-single-threaded-execution` takes effect at once, in both directions, and keeps `VSIM` and `VADD` with `CAS` on the coordinator while it is `yes`; pattern forms of `CONFIG GET` leave it out like Eski's other settings that the 7.4 server lacks. Every vector command other than the searches named above runs on the coordinator, and the keyspace workers never hold a vector set.

With a label scheme or in owner mode each element also carries its writer's label and owner, and each reader sees its own view of a set; see [Labels](labels.md#vector-sets) and [Owners](owners.md#vector-sets).

Graph-dependent results differ from the reference by design: the order of equal scores outside `TRUTH`, the members kept when `COUNT` cuts a group of equal scores, `VLINKS` neighbour lists and levels, `VINFO` max-level and vset-uid, `VRANDMEMBER` selections, payload bytes, serialized lengths and memory sizes.

Verify with `bash test/vectorset/compare.sh`, `./test/conformance/run.sh --suite vectorset --baseline test/conformance/baseline-vectorset.json`, `python3 -I test/vectorset/memory.py` and `bash test/run_packages.sh`. The [command reference](commands.md) lists supported forms and [build, run and test](build-run-test.md#vector-set-checks) describes the checks.
