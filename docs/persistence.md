# Persistence

Eski offers local RDB snapshots and append-only files (AOF). The default snapshot rules are 3,600 seconds with one change, 300 seconds with 100 changes, and 60 seconds with 10,000 changes. `appendonly` is off by default. Set `save ""` to disable scheduled snapshots. Choose a writable existing `dir`; the default snapshot name is `dump.rdb`. A matching persistence file can be loaded at startup even when no automatic snapshot schedule is configured.

## Snapshots

`SAVE` writes a synchronous snapshot and can block foreground work. `BGSAVE` uses a background child; `BGSAVE SCHEDULE` can schedule work when another persistence child is active. `LASTSAVE` and `INFO persistence` expose status. Set `save seconds changes` rules for scheduled snapshots. `stop-writes-on-bgsave-error` can reject writes after a configured snapshot failure, so monitor failures rather than treating the last client write reply as a successful backup.

```sh
mkdir -p /tmp/eski-data
./bin/eski --bind 127.0.0.1 --port 6399 --dir /tmp/eski-data --save 60 1000
```

From another terminal, write a value, request `BGSAVE`, wait for `INFO persistence` to show completion and then verify a controlled restart. Background work still has fork, copy-on-write, memory and I/O costs. Keep backups separately from a working directory that an operator can overwrite.

Snapshots and `DUMP` payloads store hashes with field deadlines as RDB types 24 and 25. Loading and `RESTORE` also accept types 22 and 23, the field-expiry encodings written by the 7.4 release candidates, because the released 7.4 server accepts them too; Eski never writes those two types. That acceptance, and the skipping of the slot-info opcode 244 in snapshot files, was confirmed against the reference server with `test/persistence/reference_probe.py`, whose recorded output is `test/persistence/reference_probe.txt`.

## Append-only files

`appendonly yes` enables an AOF in `appenddirname` (default `appendonlydir`) using `appendfilename` (default `appendonly.aof`) and its manifest/base/incremental files. `appendfsync always`, `everysec` or `no` selects synchronization policy; the default is `everysec`. A successful write reply is not necessarily an fsync acknowledgement with the latter policies. Preserve the whole AOF directory rather than selecting a single file from an active multi-file set.

```sh
./bin/eski --bind 127.0.0.1 --port 6399 --dir /tmp/eski-data \
  --appendonly yes --appendfsync everysec
```

`BGREWRITEAOF` compacts the log with a background rewrite; related rewrite thresholds and incremental-fsync options tune scheduling/I/O. Startup validates manifests and payloads and applies the configured truncated-tail policy. Inspect logs and `INFO persistence` when a load/rewrite fails. With `aof-use-rdb-preamble no` the base is written as commands and keeps everything the server holds when the rewrite starts: a hash field that has expired but is not yet removed is written with its deadline, so a hash whose fields have all expired is still a key after a reload, as it is on the running server, and a pending entry of a consumer group whose stream entry was deleted is kept by adding that entry back for the claim and deleting it again, after which `XSETID` puts the stream's counters back. `DEBUG LOADAOF` is refused with `ERR the append-only file has a failed write that is not resolved yet, so DEBUG LOADAOF is refused; check the server log` while a write or sync of the log has failed and not recovered, because a load at that moment would cut back the file the server still has bytes to append to; it works again once `aof_last_write_status` reads `ok`. `WAITAOF` can request local AOF synchronization, but reports zero replica acknowledgements; a local request fails if AOF is disabled. `WAIT` likewise reports no replicas. No network replication exists.

[Lua evaluation](scripting.md) records translated command effects, including successful writes before a later script error, rather than EVALSHA or cached source. Script effects form an AOF group and join an enclosing MULTI group; relative expiry keeps its absolute deadline on replay. The source cache is ephemeral and absent from RDB/AOF, so a restart can return NOSCRIPT even when the script's stored data was restored.

Function library definitions are saved in RDB snapshots and AOF base files. Their Lua closure/upvalue state is rebuilt from source on restart; application data that must survive restart belongs in stored values. Plain worker SET commands retain SET records. Worker hash commands retain canonical translated effects, including individual HDEL records for actual field expiry and absolute field deadlines. HINCRBYFLOAT journals the new value together with any retained field deadline. Other eligible worker commands can produce atomic RESTORE postimages with absolute expiry in AOF, which replay through the same public payload format. A key that is removed because it expired is written as `DEL` wherever the removal happens: on a read or a write that names it, in `SCAN`, in a `BY` or `GET` pattern of `SORT` and `SORT_RO`, in `RANDOMKEY`, and in active expiry. Replay runs with the deadlines in the records and never removes a key for its age, so without that record a later `SET ... NX` or `INCR` of the same name would replay against the old value. `HPERSIST` is written with only the fields it made persistent, and not at all when it changed none, so a field that had already expired stays expired after a restart.

## Search definitions and JSON values

Search index definitions and aliases for both `ON HASH` and `ON JSON` persist with the dataset. Eski rebuilds index contents from the loaded keys. Native snapshots and RDB-form AOF bases save definitions and aliases in module auxiliary records. Command-form bases write definitions before aliases and keys. These snapshot records require an Eski version that understands them. [Search](search.md)

JSON keys use the versioned Eski module type `EskiJSON_` in snapshots and in `DUMP` payloads. It preserves member order, signed and unsigned integers, exact double bits and FPHA array formats. Eski can transfer these payloads to another Eski instance with `RESTORE` or `MIGRATE` where access rules permit. Use JSON text to move documents between Eski and Redis. [JSON documents](json.md)

The incremental AOF records JSON writes using their original arguments when they change a document, including a partial change followed by a deterministic command error. JSON is supported in both base rewrite formats. In a command-form base, Eski uses root `JSON.SET` for values that replay exactly from text, and native `RESTORE` for stored representations that require it, including FPHA arrays. Key deadlines travel with either form.

## Payload transfer and shutdown

`DUMP` returns a serialized key payload without its key TTL. `RESTORE key ttl payload` validates that payload and accepts `REPLACE`, `ABSTTL`, `IDLETIME` and `FREQ` under their option checks. Use a binary-safe client. `MIGRATE` transfers keys to another endpoint using payload restore, with `COPY`, `REPLACE`, `AUTH`, `AUTH2` and multi-key `KEYS` forms. Transfer is an explicit client operation; it does not establish continuous replication or cluster failover.

`SHUTDOWN` supports save/no-save and related shutdown controls. A deliberate `NOSAVE` can discard changes not present in durable files. Never use shutdown or restore as an unreviewed probe against an existing instance.

## Labels and owners

A server with a [label scheme](labels.md) or [owner mode](owners.md) writes snapshots that keep both. The file is an ordinary snapshot of format version 12 with three kinds of record added in the module auxiliary framing, under the module name `eski-labl`: a header before the function libraries and the first database, one partition record before the keys of each label and owner, and one copy order per database after its last partition. The header holds the mode (labels, owners or both), the label scheme and the table of labels in the same encoding the label package uses, the label quotas, the owners that hold a key or have a quota with their quotas, the forget sequence the file covers and a dataset seed. A partition record names a label and an owner by their positions in the header, and the keys after it, with their ordinary payloads, expiry and access hints, belong to that partition. The copy order lists, for every name held at two or more labels of one database by the shared data or by one user, the labels in age order, because a reader that sees two copies of equal rank reads the older one and must read the same one after a restart. A server without labels and owners omits these access records. An older Eski and the reference both refuse a labelled file at startup, as it names a module they do not have.

A labelled file loads only on a server in the same mode, and every mismatch is refused at startup with a line that names the file and says what to change: a file without labels or owners on a server with them, a labelled file on a server without them, and a label-only file and an owner-mode file on a server in the other mode. Labels are matched by position: the configured scheme must give every level, compartment and trust level of the file the same name at the same position. A configuration with more names than the file loads it, a file with more names than the configuration extends the server's scheme to the file's, with a log line that suggests `CONFIG REWRITE`, and a different name at any position is refused with a line such as `names level 3 SECRET and the configured scheme names it SECRET2`. Owners are matched by their ids. `label-partitions-max` and `owner-partitions-max` apply while loading and name themselves when a file needs more partitions; byte quotas and `maxmemory` do not, as data that was admitted is not refused at load. Keys that expired while the server was down are dropped after the copy orders were checked against the file as written, and leave no partition or owner entry behind.

The loader treats the file as untrusted: it checks the header's version, mode and scheme, that the mode flags agree with the scheme in the same header (a file that says it has no labels carries the one-level scheme), every quota, owner id and count, every label and owner position, that each partition appears once, that every key sits in a partition, that each copy order lists two or more copies, each once, exactly the partitions that hold the name, and that no name sits in two partitions without one. Every count is checked before it is looped over: a header lists at most one quota per label of its own label table (at most 65,535) and at most as many owners as there are owner ids, a copy order lists at most half as many names as its database has key records, each with at most as many labels as the table holds, and every check for a repeated entry takes time in proportion to the count. A file that fails a check stops the start, or the server during `DEBUG RELOAD`, with the byte offset and the reason; log lines name an owner by its position in the file, never by its id. `DEBUG RELOAD NOSAVE` first checks the mode and scheme of the file it is about to load, including whether a longer scheme in the file could be adopted, and answers an error without flushing when they do not match, also on a server without labels; a file that is refused only after keys were read from it, such as one whose labelled header follows its first keys, stops the server instead of leaving it half loaded. With labels or owners, `DEBUG RELOAD MERGE` and `NOFLUSH` are refused.

While a labelled or owner-mode server loads its file at startup it answers the commands that are allowed during loading, but nothing they do reaches the data being loaded: `DEBUG` answers the loading error, the label scheme settings and `owners` cannot be changed until the load ends, eviction waits until the load ends, and every key is counted towards its owner whatever was served in between.

At startup a labelled or owner-mode server removes temporary snapshot and rewrite files that a crash left in its working directory: the names `temp-<pid>.rdb`, `temp-rewriteaof-<pid>.aof` and `temp-rewriteaof-bg-<pid>.aof`, where `<pid>` is a process number with no running process, and never the file that `dbfilename`, `appendfilename` or `appenddirname` names. A labelled or owner-mode snapshot and its temporary file are created readable and writable by the server's user only (mode 0600), because they hold every label's data and every owner id; without labels and owners the files keep the mode they always had.

`RESTORE` on a server with labels or owners always checks its payload in depth, whatever `sanitize-dump-payload` says, because every writer may restore there and a malformed payload could otherwise be read past its end; loading a snapshot file follows the setting as it always did, and without labels and owners `RESTORE` follows it too.

A vector set in a labelled or owner-mode snapshot is stored partition by partition. A set has a key in every label and owner partition where it holds elements, and the value of each of those keys in the file is the version 2 encoding of that one partition of the set (see [Vector sets](vector-sets.md)): its elements with their slots, sequences, vectors and attributes, its graph when it has one, its free slots and its level generator state, together with a number that the file gives to each set object at its first partition. That number joins the partitions of one set again at load, so two sets that live under one name at scopes that cannot see each other stay two sets, and the key name, database and set parameters must agree for every partition of one number. An element whose name is held in two or more partitions of the same set also carries its age among those copies, so a reader that sees copies of equal rank keeps reading the same one; the loader checks those ages over the whole file, including partitions it drops, before it puts the copies that remain back in their order. Each partition keeps its kind: a flat partition, a graph partition, the graph that a shared partition at the lowest label may hold for its whole set, and a user's small block reload as they were saved, whatever their size. A partition whose key expired while the server was down is read and checked like the others and then dropped, and a set all of whose partitions were dropped is never created, so the loaded data looks as if the expired partitions had never been written. After a restart every reader's replies from `VSIM`, `VLINKS`, `VINFO`, `VCARD`, `VEMB`, `VGETATTR`, `VRANGE` and `VISMEMBER` are the same as before it, and later writes build the same graphs as on a server that did not restart.

The vector set dataset seed, from which the level generators of new sets and new partitions are derived, survives a restart. The labelled header carries it in its last field, which reads 0 while no seed has been drawn. Without labels and owners a snapshot carries it in an auxiliary field named `eski-vset-seed`, as a decimal number, written just before the first vector set in the file and only when the server holds a seed, so a file without vector sets has the same bytes as before. A seed read from the file replaces the server's seed when the load completes and takes precedence over `label-stream-seed`; after a load from a file without a seed the server draws or derives one again when a set needs it. An `eski-vset-seed` field that is not a decimal number between 1 and 18,446,744,073,709,551,615 written without leading zeros, that appears twice, or that appears in a labelled file stops the load.

**`DEBUG DIGEST-SCOPES`** exists only while a label scheme or owner mode is configured; without them the subcommand is unknown and `DEBUG HELP` does not list it. It answers one 40-character hexadecimal signature of everything a snapshot or the append-only file has to keep: every copy of every key with its value, its scope (label and owner), its expiry deadline and its age among the copies of the same name, every partition of every vector set with that partition's contents, the label quotas and the owner quotas, and, once a user has been forgotten, the forget sequence. The parts are combined by addition, so the signature depends on what the server holds and not on the order of the copies in memory, on how the tables have grown or on the order in which the data was written. `DEBUG` is a top-only command, so it needs a top login (in owner mode one with `owner-operator`, see [Labels](labels.md#what-is-enforced-in-this-release)), the debug command must be enabled with `enable-debug-command`, and while a file is loading it answers `LOADING`. It exists to prove persistence: the signature taken before a save, a rewrite or a shutdown must equal the one taken after the restart, after `DEBUG RELOAD` and after `DEBUG LOADAOF`, and it also moves when only a scope, a deadline or a copy's age changes, which a comparison of the keys one login can read would not show because no single login reads every scope.

The access rules of saving, `LASTSAVE`, `INFO persistence`, `DUMP`, `RESTORE`, `MIGRATE` and the rule that `CONFIG SET` needs a top label are in [Labels](labels.md#what-is-enforced-in-this-release), and the forget sequence and the snapshot that follows `OWNERS FORGET` in [Owners](owners.md#persistence-and-forgetting). The append-only file of a labelled or owner-mode server is described in the next section, and encryption of the files in [Encryption of the data files](#encryption-of-the-data-files).

### The append-only file

A server with a label scheme or owner mode keeps an append-only file, either started with `appendonly yes` or switched on at runtime, in the same layout as without labels: a manifest, one base, incremental files and history files. Three things differ: what a record carries, what the base is, and what the loader accepts.

**Records.** Every record that changes data starts with the scope of the change. On a label-only server that is `LABEL AS <marking>`; in owner mode it is followed by `OWNER <id>` when the change was made for a user and by `SHARED` for shared data. The marking is the canonical text of the label, with `;TRUST` only when the trust is above the lowest. A record has no owner word when an operator at the top label wrote it without naming anyone, which is how a flush that removes everything is told from one that removes a single user's or the shared data. What the server does on its own, such as an eviction, a quota eviction or the expiry of a hash field, is written with the scope of the partition it removed from. Records that concern the whole server carry no scope: `FUNCTION LOAD`, `DELETE`, `FLUSH` and `RESTORE`, `SWAPDB`, `OWNERS FORGET <id>`, `OWNERS QUOTA <id> LIMIT <n>`, `LABEL QUOTA <marking> [TRUST <trust>] LIMIT <n>`, always with the words in that order, and `CONFIG SET label-levels`, `label-compartments` or `label-trust-levels` followed by the whole new list, written after a runtime rename or extension of the scheme succeeded. A transaction or a script is written as `MULTI`, records that each carry their scope, and `EXEC`; the command records of one group name one scope, and the only exceptions are single deletions of one key or one hash field, which keep the scope of the partition they delete from. A key removed because it expired, by a command or by active expiry, is written as a deletion with the scope of its partition, as without labels, because replay does not read the clock and would otherwise keep it.

When a command that is going to be written passes an expired copy of a name while it resolves it, for example a write at a high label that passes an expired copy of the same name at a lower one, a store command that reads past an expired source, a declassification onto an expired target or `VADD` over an expired presence, the log also gets a record that deletes that copy at its own scope, just before the command's record and in the same group. Nothing is deleted, counted, announced or notified when it is written, so no reader can tell it was written; it exists so that replay, which never reads the clock, reaches the outcome the running server reached. A `SORT ... STORE` whose `BY` or `GET` pattern reads a hash field that has expired in a hash at another scope is written as its result instead of as itself: a deletion of the destination followed by pushes of the stored values, at the command's scope, so replay never reads that field, and the other scope's hash is left exactly as the running server left it.

Every incremental file starts with a marker record of 43 bytes, `ESKI-ACCESS 1 <labelled> <owners>`, each flag 0 or 1, before anything else, the timestamp lines of `aof-timestamp-enabled` and the first `SELECT` included. A vector set seed is written as `ESKI-VSET-SEED <number>` when it is drawn and at the head of each new incremental file while one is held. A log without labels and owners is unchanged apart from that seed record, which it gains only once vector sets are used.

**The base is always a snapshot.** Every partition, copy order and vector graph goes through the one snapshot writer, so a labelled or owner-mode server never writes the command form of a base. `aof-use-rdb-preamble no` stops the startup when `appendonly yes` is set and is refused by `CONFIG SET` while labels or owners are on, with `the append-only base of a server with a label scheme or owner mode is always a snapshot`; so is `CONFIG SET appendonly yes` while it is `no`. `BGREWRITEAOF` and the automatic rewrite (`auto-aof-rewrite-percentage` and `auto-aof-rewrite-min-size`) work as they do without labels: the new incremental file is opened with its marker, a child writes the base from the state at the fork, every record written while the child runs goes to the new file with its scope, and a finished rewrite retires the older files to the history, which is deleted. The files of a labelled or owner-mode log are readable and writable by the server's user only (mode 0600, the directory 0700), because they hold every label's data and every owner id. This holds on every path that brings a mode and a log directory together: a start, the log turned on at runtime while a mode is on, a mode turned on at runtime while the log is on, and an old single-file log moved into the directory at a start; a directory that already existed with wider modes is narrowed then, together with the log's files in it. Without labels and owners the modes stay 0644 and 0755.

`CONFIG SET appendonly yes` works on a labelled server: the base is written by a background rewrite from the keys held at that moment, and the log is on when it finishes. Turning a scheme or owner mode on while the log is on keeps the rule that the server holds no key; before it answers, Eski rewrites the log in the new mode on the spot, so that the base and a fresh incremental file carry the new marker. A runtime rename or extension of the scheme does the same, as a snapshot is saved before the answer: with the log on, the change pauses the server for one write of the dataset, and the base of the new files carries the new names, so a log never holds names that its base lacks. The new base and a fresh incremental file are written first and enter the manifest together, in one replacement of it, and the new marker goes into that file only then: until that step a failed write or a crash leaves the log exactly as it was, loadable with the old mode and names, and after it the log is complete in the new mode, so a crash in the middle of the change leaves one of the two logs and a restart loads it with the mode and names of that one. Both are refused with `the append-only file with the new label scheme or owner mode could not be written; check the server log` when the rewrite fails or when the command runs inside a transaction, and the old scheme stays in force (when snapshots are in use too, the snapshot is saved first, and the restoring pass that follows a refused `CONFIG SET` saves it again with the old scheme, so no file keeps names that the configuration lacks). The change is also written as a scheme record, which stands behind a base that already has the names and is therefore replayed as a change of nothing; the loader still applies such a record under the runtime rules (names can be added and renamed, never removed or reordered, and a new name must be new to the scheme), for a log whose base is older than the record.

**Replay.** The loader reads the marker, then runs every record at the scope it names with the same handlers a client reaches, and it is a function of the file alone: it runs no login, ACL, ceiling or token check, no quota check and no eviction, because a record in the log was admitted when it was written. It does run the keyspace's write rule: a record that writes a name its scope sees held at another scope, without a live copy of its own, is one the running server answers with `INUSE`, and it refuses the whole file, so a damaged or crafted log can never change a copy at another scope. Two kinds of record are let through. A deletion of one key or one hash field acts only on its own partition and is skipped when that partition does not hold the name, because the log may hold such a deletion twice. Inside one group, a record may write a name whose own copy an earlier deletion in the same group removed, at its own partition only; this is how a command that emptied its own hash by removing an expired field and then wrote it again, or a `SORT ... STORE` written as its result, is replayed, and the copy keeps its age among the copies of its name as it did on the running server. It creates the partition a writing record needs and refuses only a record that needs more partitions than `label-partitions-max` or `owner-partitions-max` allow. A record without a scope is accepted only in the forms above, a record that names a command that writes nothing is refused, and so is a handler that answers an error. The loader refuses the whole file, never part of it, and names the byte offset of the record, never an owner id, a marking or a value, in these cases: a file without its marker as the first record, a marker that is not the first record, has another form or version, or names another mode than the server's; a scoped record on a server with neither labels nor owners; a marking that does not parse in the scheme reached so far; an `OWNER` or `SHARED` word in label-only mode; an owner id that is empty, longer than 128 bytes, or has a space, a control byte, a byte above `~` or is `*`; a prefix inside a prefix, around `MULTI`, `EXEC`, `DISCARD`, `SELECT`, the marker or the seed, or around an operator record; two scopes among the command records of one group; a record without a scope that is not an operator record, `CONFIG SET` of any setting but the three scheme settings, or of two settings in one record; a scheme change that the runtime rules refuse, or one that would turn labels or owners on; a seed record that is not one number from 1 to 18,446,744,073,709,551,615, or that differs from the seed already held; a record that the write rule refuses. A start that is refused exits with status 1; `DEBUG LOADAOF` answers `ERR Error trying to load the AOF files, check server logs.` and leaves the keyspace empty with the server up.

A file loads only on a server in the mode it was written in. A plain file on a labelled or owner-mode server and a labelled or owner-mode file on a server without labels are refused with the same lines as for snapshots, and so are a label-only file on an owner-mode server and the reverse. At the end of a replay the scheme the server holds is the base's scheme moved on by the scheme records, and the base must agree with the configured names at every position the base has, as for snapshots. A restart from the log therefore accepts a configuration that has fewer names than the log reached, which the log then extends (with the log line that suggests `CONFIG REWRITE`), and refuses one that names a position differently from the base, with the line that names the position and asks for the file's names; both follow the rules for snapshots. After a runtime rename the base already has the new names, so a restart whose configuration carries them (`CONFIG REWRITE` after the change, or the new names written by hand) starts and gives every reader the same replies as before, and a restart with the old names is refused until the configuration is changed to the file's names. `DEBUG LOADAOF` works right after a change.

**Torn tails.** `aof-load-truncated yes` keeps its meaning at the granularity of a record, and a group is one unit. A tail that ends inside a scoped record, or inside any record, is cut back to the end of the last whole record. A tail that ends inside a group, after `MULTI`, between its records, after a deletion record that belongs to the command after it, or inside `EXEC`, is cut back to before `MULTI`, so the command and the deletion that was written for it are both dropped and the state is the one before the group. A tail that ends inside the marker cuts the file to nothing, and the server writes a fresh marker. A write batch never ends inside a group when the write succeeds, so a torn group is only ever a crash or a failed write. Every one of these cases loads a state the running server was in between two acknowledged writes. A tail torn in a file that is not the last one is fatal, and with `aof-load-truncated no` any torn tail stops the start with the offset.

**Forgetting.** `OWNERS FORGET` writes its record and takes the next number of the forget sequence. `INFO persistence` at operator top shows `owners_forget_in_aof`, the sequence at the start of the last rewrite that finished, counted only once the files from before that rewrite are gone from the directory; at a restart it starts at the number in the base once the history the manifest lists is gone. While the log is off it equals the sequence only when the log directory holds no file of a log (and no old single-file log is in the working directory); when files of an earlier log are still there, because the log was turned off at runtime or the server started without it beside an old directory, the field keeps its last value, and a warning at the forget and again when `owners-forget-aof-delay` has passed names the directory. Eski does not delete those files while the log is off: delete them, or turn the log on, which rewrites them. Eski rewrites the log itself `owners-forget-aof-delay` seconds after a forget (hidden, default 300; several forgets within the delay share one rewrite, and 0 leaves it to the operator, who runs `BGREWRITEAOF` and reads the field). The rewrite that counts is one that started after the forget: a forget that happens while a rewrite runs is covered by the next one. When the rewrite finishes, the history files that held the forgotten user's records are deleted, whatever `aof-disable-auto-gc` says, as long as a forget is not yet counted, so no file of the directory has the id or the user's data any more when the field moves. A clean shutdown with a forget that no rewrite covers rewrites the log before it exits, and `SHUTDOWN NOSAVE` skips that and logs that the files still hold the data. At startup a labelled or owner-mode server, and any server with an encryption key, removes the temporary files that a crash left in the log directory and every log-named file there that the manifest does not list, because they can hold forgotten data or data from before the key.

**`DEBUG LOADAOF`** reloads the log on a labelled or owner-mode server like `DEBUG RELOAD` reloads a snapshot: it needs a top login, it checks the base's scheme and mode before it flushes, and it keeps the forget sequence. **What stays refused:** `MIGRATE` (its cached connection would write at whatever login the target holds), a command-form base, and the persistence commands below top. A reader below top sees no reply, counter, `INFO` field, notification or log line that moves because the log or a rewrite holds hidden data; the sizes and times of files and rewrites, a failed write and the disk they fill belong to the disk class described in [Labels](labels.md#what-comes-next).

## Encryption of the data files

With `encryption-key-file <path>` set at startup, every data file Eski writes is encrypted and authenticated: the snapshot written by `SAVE`, `BGSAVE`, the save points, the shutdown save and `DEBUG RELOAD`, and in the append-only directory the base, every incremental file and the manifest, whether a background child or the server itself writes them, together with every temporary file on the way (`temp-<pid>.rdb`, `temp-rewriteaof-bg-<pid>.aof`, `temp-rewriteaof-<pid>.aof`, `temp-<appendfilename>.incr` and `temp-<appendfilename>.manifest`). Nothing of a key name, a value, an owner id, a label name or a label marking is readable in those files without the key, and no byte of them can be changed without the change being noticed when the file is read. Without the setting the files are the plain files described above, byte for byte. The setting cannot be changed at runtime, and with labels or owners it applies the same way to their files.

**The key file** holds 32 random bytes written as 64 hexadecimal characters, optionally followed by one newline, for example made with `openssl rand -hex 32 > eski.key` and `chmod 400 eski.key`. The start is refused, with a line that names the file and the rule, when the file cannot be opened or read, is not a regular file, holds anything else, can be read or written by its group or by other users (its mode must allow its owner only, such as 0400 or 0600), or belongs to a user other than the one the server runs as or root. A symbolic link is followed and the file it leads to is checked. The key is read once at startup into memory that is kept out of core dumps, it is wiped at a clean exit, forked children inherit it, and it never appears in a log line, a reply or a file. `CONFIG GET encryption-key-file` answers the path, by its exact name only. In a container, mount the key read-only as a file owned by the user the server runs as with mode 0400: with `docker run`, bind-mount a host file that already has that owner and mode (`--mount type=bind,src=/srv/eski.key,dst=/run/eski/key,readonly`); with Compose or swarm secrets, give the secret `uid` of the server's user and `mode: 0400`; on Kubernetes, use a secret volume with `defaultMode: 0400` when the server runs as root, or have an init container copy the secret into a volume and set the owner and mode there, because a secret volume shared through `fsGroup` is readable by the group and is refused.

**How a file is sealed.** Each file starts with a 58-byte header: the 8 bytes `ESKIENC1`, a kind byte (1 for a snapshot, 2 for an append-only base, 3 for an incremental file, 4 for the manifest), an algorithm byte (1 for AES-256-GCM), a 16-byte key id and a 32-byte salt drawn at random for that file. The key id is the first 16 bytes of HKDF-SHA256 of the key with an all-zero salt and the text `eski key id v1`, so a file written under another key is recognised before anything is decrypted. The file's own key is HKDF-SHA256 of the key with the file's salt and the text `eski snapshot v1`, `eski append v1` or `eski manifest v1`, so no two files share a key. The rest of the file is a run of segments, each a 4-byte little-endian length word, the encrypted bytes and a 16-byte tag. A segment's 12-byte nonce is its index in the file as 8 little-endian bytes, a byte that is 1 only for the closing segment of a closed file, and three zero bytes; the header and the segment's length word are authenticated with it. A snapshot and a base are cut into segments of at most 64 KiB and end with a closing segment; an incremental file gets one segment for each write the server makes to it, and a write larger than 64 KiB is cut into several segments whose length words carry the top bit, which says that the next segment belongs to the same write; the manifest is one closing segment. A segment is sealed once: when a write fails, Eski writes the same sealed bytes again later and never seals other data under an index it has used, and after a restart it always opens a new incremental file instead of adding to an existing one. The manifest lists the salt of every file, and when a new incremental file is opened it also records the length the earlier incremental files have, so a file cannot be replaced by another file of the same kind under the same key, and only the newest file has an end that is not authenticated.

**What the server does with each file:**

| Situation | Result |
| --- | --- |
| No key, plain files | loaded as without encryption |
| No key, an encrypted file | the start is refused: `the data file is encrypted; set encryption-key-file` |
| A key, a file written under another key | the start is refused: `the data file was written with another key` |
| A key, a damaged or shortened snapshot or base | the start is refused, with a line that names the file, the segment and its byte offset |
| A key, a damaged segment of an incremental file, or an incremental file that is not the newest and differs from its recorded length or salt | the start is refused, with the same kind of line |
| A key, the newest incremental file ends inside its last write | `aof-load-truncated yes` cuts the file back to the start of that write and loads the rest; with `no` the start is refused and the file is left as it was |
| A key, a plain file | the start is refused: `the data file is not encrypted although encryption-key-file is set`, unless `encryption-adopt-plain` is set |

A segment that is complete but fails its check is treated as damaged even at the end of the newest file, as a crash leaves a write cut short and never a whole segment with other bytes. `DEBUG RELOAD` and `DEBUG LOADAOF` apply the same rules to the files they read, except that the two switches below act only while the server starts. `DEBUG RELOAD NOSAVE` checks the snapshot first and answers an error without flushing when it would refuse it; `DEBUG LOADAOF` checks the base first in that way only with labels or owners on, as described above, and otherwise flushes before it loads, as it does without encryption.

**Turning encryption on and changing the key.** Two settings, each meant for one start, cover the cases the table refuses. `encryption-adopt-plain yes` lets a start with a key load plain files; right after the load Eski saves the snapshot again under the key (when the snapshot was loaded, or when a plain `dbfilename` is present) and rewrites the append-only file under the key when it is on, and it deletes the plain files it replaced, history files included, whatever `aof-disable-auto-gc` says. `encryption-key-file-previous <path>` names the key the files were written with; the start opens those files with it and writes them again under `encryption-key-file` in the same way. The previous key file must follow the same rules and hold a different key. Either setting left in place makes the next start fail, with a line asking to remove it, once no file needs it; if the server stops before the new files are written, the next start with the setting still in place does the work again. Eski removes only the files it owns and names in the log what remains the operator's: copies and backups made before the change still hold the data in its earlier form, and they stay readable to whoever has their key, or anyone when they are plain.

**Out of scope.** Key rotation beyond the previous-key switch, key services and hardware modules are not offered. The encryption does not detect that whole trailing writes were removed from the newest incremental file by someone who can write to the directory, nor that a complete older set of files was put back; it does not hide the sizes of files and segments, the timing of writes or the file times. The server log, the label audit file, `DUMP` payloads, `MIGRATE` traffic, replies, the ACL file and the configuration file are not data files in this sense and stay as they are, and data in memory and swap is not covered. Files and copies made before encryption was turned on are not reached by it.
