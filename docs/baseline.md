# Baseline measurement plan

`bench/baseline.py` defines every measurement that the later efficiency work starts from. Its `steps(context)` returns one step per measurement; the one-host run entry point, `tools/rented_run.py`, runs them after the correctness phase on the same host, one at a time, each as its own stage. A step starts and stops its own servers and containers, writes only under `<run>/<step>/`, and leaves nothing running when it passes, fails or is killed: every server and container it starts is registered with a watcher in its own session, which removes whatever is still registered when the step's process group dies. A step can be rerun alone. This page describes the plan as built; it holds no figures.

The plan has two profiles with the same steps. `full` is the measurement. `rehearsal` runs every step through the same code at toy sizes, so the whole plan finishes in about a quarter of an hour on a laptop; its results carry `"qualifying": false` and a note that their figures are not read.

## What every step writes

Each step's artifact is `<run>/<step>/result.json`, whose top-level `exit_code` is 0 only when the step passed, and everything else a step writes lies under `<run>/<step>/`. The run entry point is the only runner of the plan. `bench/baseline_run.py` is not a second one: it runs one step's driver, repeated as the step asks, and serves what the entry point does not, namely the repetitions, the per-repetition telemetry and memory records, the inventory of raw outputs and the cleanup watcher. Steps that wrap a driver this way keep, for every repetition, the driver's own JSON output, its log, the sha256 of every file it wrote, the memory every server reported just before it stopped (the engine's `INFO memory`, the resident and peak resident size of the server process from `/proc/<pid>/status`, and for containers the kernel `memory.peak` of their cgroup), and machine telemetry sampled every two seconds: package temperature, throttle events, the idle share of each server and client CPU and every process outside the run that used a tenth of a core on one of them. A host record at the start and the end of each step gives the kernel and its command line, the microcode, SMT and transparent huge page settings, the frequency policy of every role CPU, the load, memory, and the type and free space of the filesystem that holds the run.

## Method

The stock comparison uses the method of `bench/testbed/design.json` and the exam scheduler without the remote installation: `bench/stock_exam.py` builds a run root on the host with copies of the harness, the qualified binary, a profile that pins every image by its local ID and the plans of both phases, picks the design with four client threads when the host gives four client CPUs, takes the first server CPU as the one server core and a CPU outside both roles as the controller, and runs the idle watch, the calibration and the benchmark phase with every gate of the design. A gate that is not met holds the step instead of producing a number. Every timed run keeps the raw memtier output with its full histogram, the compressed histogram in its JSON and its per-second counts. A calibration case that is not valid stops the step before the benchmark phase.

Eski runs natively while the competitors run in containers with a memory cap. Native is the primary measurement because the run qualifies one binary, built by the host's own compiler, and the image that `bench/image.sh` builds compiles the source again with the Dockerfile's pinned compiler, so it would measure another binary. Every engine gets the same server CPU, the same maxmemory and persistence off, and the clients and the network path are the same for all; the native Eski process has no container memory cap, which the measured workloads never approach. Memory is reported in the terms that apply to each: the container memory peak and the peak resident size of the server process for the competitors, the resident and peak resident size for Eski, and the engine's own `INFO memory` figure for all.

The search, JSON and vector set comparisons send the same seeded data and the same requests to Eski and to the pinned Redis 8.10.3 image. Before anything is timed, both engines are started side by side, loaded and indexed, and every distinct request of the plan is sent to both and its replies compared exactly. A request shape whose replies differ is not timed, unless the difference is a named one that the output records and counts: the neighbours an approximate HNSW graph returns; the order of documents with equal scores, where a reply that also differs in a score or in the keys of a complete group of equal scores still counts as unexpected; and JSON number arrays that the reference prints in half precision, where a reply that still differs after rounding both to half precision counts as unexpected. Three normalizations that remove what the engines never share are declared in the output: search projections are compared as field sets, FT.HYBRID's `execution_time` is removed, and cursor ids are removed. Each timed repetition then starts one engine fresh, loads the data, builds the indexes over the existing data and records the build time and the memory before and after, runs a warmup, and runs the planned requests over one connection and over several connections in separate client processes, recording every request's latency, its shape and whether its reply equalled that engine's verified reply. Requests that change data restore it within the request and touch keys owned by one connection, so their replies do not depend on interleaving. The engine order alternates by repetition.

`bench/persist/engine_compare.py` gives Eski, Redis and Valkey the same mixed dataset on a directory of the host disk, so fsync reaches the device, and checks the restored data against the saved data and across engines. The noise floor step runs `bench/ab.py` with the qualified binary on both sides and writes the floor record that `bench/ab_report.py --floor` accepts, so later comparisons on the host know the smallest difference they can believe. The trace steps run each workload area against the debug-information build of the same source, started as a child of `perf record` with DWARF call graphs, or frame-pointer call graphs where DWARF is refused. A host without `perf` or without permission to use it fails these steps with that reason; a host that permits sampling but not call graphs records a flat profile and still fails the step, naming the refusal, so the call graphs stay owed.

The specification step fetches the pinned archive of the Redis benchmarks specification from GitHub and checks its sha256, probes which commands Eski and Redis implement, and takes for every command group the case with the highest priority whose clients fit the client CPUs; groups without such a case are listed in the step's result. Its cases run through the same exam scheduler and gates as the stock comparison.

## Time and disk

The steps carry an estimate computed from their configured sizes, durations and repetitions and the planning constants in `bench/baseline.py`; the full plan adds up to about 10.5 hours, of which the stock comparison and the specification cases are about 7, plus about half an hour when the noise floor runs sequentially on a host with one server CPU. The full plan writes about 2.5 GB: about 0.7 GB of per-second machine samples and raw client output for the stock comparison, about 0.3 GB for the specification cases and their archive, about 1 GB of perf data for the seven trace steps, and less than 0.5 GB for everything else, including a copy of the debug build in each trace.

## Not covered

The module lists what the plan leaves out and why in `UNCOVERED`: an Eski container target, multicore scaling outside the compute thread step, search features Eski does not implement, FT.PROFILE, highlighting and summaries and DIALECT 4 paging whose replies differ by design, FT.HYBRID fusion, whose replies differed from the reference when the plan was built and which is therefore checked on every run and timed only once they are equal, a labelled-mode A/B against an older tree, and the tools that need a second binary, a workstation or network access rather than the host.
