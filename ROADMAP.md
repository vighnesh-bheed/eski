# Roadmap

Eski implements a single-node command surface and verifies it through package tests, differential harnesses, smoke comparisons and an upstream-suite baseline gate. The generated [conformance report](docs/conformance.md) records the current gaps. An implemented group remains subject to that evidence; it does not imply that every selected upstream test passes.

## Command-group milestones

| Bitmaps and HyperLogLog | Bit operations, fields and probabilistic cardinality are implemented; completion requires `bitops`, `bitfield`, `hyperloglog` and the corresponding native/model checks. See [bitmaps and HLL](docs/bitmaps-and-hyperloglog.md). |

| Pub/sub, notifications and tracking | Subscription delivery and local invalidations are implemented; completion requires `pubsub`, `pubsubshard`, `tracking` and channel/output-buffer comparisons for the supported single-node behaviour. See [delivery and tracking](docs/pubsub-notifications-tracking.md). |

See [scripting](docs/scripting.md). |
| Persistence | RDB, append-only files and payload transfer are implemented; completion requires `dump`, persistence/codec tests, restart/corruption checks and the smoke persistence round trips. See [persistence](docs/persistence.md). |

The next compatibility work is to resolve the implementation differences identified in the expanded suite, including selected list mutation counters, query-buffer resizing/accounting, pause/expiry interactions and introspection results. Cases that require excluded features remain labelled separately. Changes should retain the supported reply and persistence behaviour and preserve the existing baseline pass set.

## Efficiency work

The first compute-worker stage offloads eligible large LCS calculations over coordinator-owned snapshots. It has bounded jobs/reservations, per-connection order, synchronous transaction/loading/tracked-source fallback and explicit cancellation/fork/shutdown ownership. That stage was qualified separately at `83024e3`; its [threading checks](docs/threading.md#correctness-checks) include deterministic kernel overlap, independent LCS expectations, external-client lifetime/order regressions, sanitizer coverage and a recorded bounded scaling comparison. Workers are opt-in. The existing benchmark tables describe their historical run.

The next stage implements worker-owned GET and exactly three-argument SET for strings without expiry or absent keys. A key has one worker owner and a FIFO request stream; the coordinator retains sockets, admission and replies. Other commands, transactions, expiring/nonstring values and observing features use a reconciliation barrier and the coordinator. The startup controls remain default-disabled. Requested directory/value/task memory is bounded separately from RSS, and retained legacy copies, allocator retention and draining barriers have memory/latency costs. See [keyspace workers](docs/threading.md#keyspace-workers).

At threading checkpoint `78eb2f1`, ten native ownership tests passed in strict debug, ASan with leak detection and TSan. The dedicated 20-case keyspace driver passed against release, address-sanitized and thread-sanitized servers. The package gate passed all 90 runs; smoke passed all 2,428 checks in each worker configuration. Both configurations preserved all 1,504 Tcl baseline passes with zero regressions and retained the existing 20 expanded failures. These results precede the new Lua work. No keyspace-worker benchmark has been run or speedup claimed; prior LCS results and recorded conformance/benchmark data apply to their earlier source. Commands beyond guarded GET/plain SET, multi-key worker scheduling and broader expiry/eviction/persistence participation still need explicit ownership and atomicity designs. The separate Rust coordination layer does not supply these single-process guarantees.

Trace and profile the accepted command path with the benchmark harness first. Use the measurements to choose one coherent improvement at a time, with its workload, allocation/memory effect and expected observable change stated before implementation. Compare each improvement against a clean recorded run under the same resource assignments and report the measured ratio for that workload. Keep negative results, client limits and excluded cases visible.

The dedicated-machine container exam follows measured improvements. Its frozen design, CPU assignments, equal memory caps, idle/temperature/power gates, rotated engine order and receipt-verified collection live under `bench/testbed`. The [benchmark documentation](docs/benchmarks.md) explains how the committed report was obtained and how to prepare another run. The roadmap promises no dates or universal performance target.

## Scope boundary

Eski remains a single-node engine. Lua evaluation is included with an embedded C runtime, explicit library/command limits and Lua 5.5 language behavior; it does not imply full Lua 5.1 scripting parity. Executable function libraries, modules, network replication, Sentinel and Cluster remain excluded. FUNCTION compatibility replies describe a server with no executable libraries; WAIT-related replies do not create replica durability. Local transactions, blocking operations and persistence remain part of the engine.

Distributed placement, routing, failover and managed operation belong to a separate coordination layer, planned in Rust. That layer is not implemented in this repository. Keeping this boundary explicit lets the engine's tests and measurements describe one node's actual guarantees.
