How the numbers were taken

Dataset. 100,000 keys with numeric ids 1 to 100,000 under one prefix, loaded by one connection at pipeline 32 before every measurement. String workloads hold one value per key; HGET, SISMEMBER and ZSCORE keys hold 16 fields or members and read field or member 8. DBSIZE and sampled replies on keys 1, 50,000 and 99,999 are checked before the warmup.

Engines. Eski, Redis, Valkey and Dragonfly each run in a fresh container per measurement with the same CPU set, an 8 GiB memory and swap cap, 6 GiB maxmemory, persistence off and host loopback networking. Dragonfly runs one proactor thread on its single core.

Fill. A separate fill of 10,000,000 keys of 64 B at pipeline 32 per engine, with the same server core and memory caps, reports the worst request during the fill and the resident and used bytes per key, read once used memory has been stable for three seconds and the server reports no keyspace rehash in progress, at most sixty seconds after the fill.

Gates. Before every case the CPU package must be at or below 55 C, the server and client CPUs at least 95 percent idle, the readings stable for 10 seconds and at least 30 seconds must have passed since the last case; an unmet gate after 600 seconds holds the run. During a case the machine must expose readable telemetry, no thermal throttle counter increments, an unchanged frequency policy, a package at or below 90 C and no competing CPU load. The machine has no battery or ACPI power-supply device; the power gate records that absence instead of an AC online reading.

Power gate. The power gate was no-power-supply-devices: the machine had to expose no power supply device at all, and a battery, mains or other power supply device seen in any sample before or during a case held the run or invalidated that case.

Isolation. Docker CPU sets and memory caps separate the roles but share the kernel, the last level cache, memory bandwidth, power and cooling. Simultaneous multithreading is off, so no role shares a physical core.

Latency. Closed loop client observed latency; p99 is the per run percentile, never pooled across runs.

Memory. The kernel memory.peak of the server container read just before it stops: it covers preload, warmup and the timed run and is not live key memory or process RSS.

Publication. Medians over the valid repetitions with the observed minimum and maximum. Excluded repetitions stay visible with their reason. There is no overall score and no cross workload average.

Quality. A measurement whose raw client output reports a maximum latency beyond 120 seconds is invalid as a histogram range artefact. The timed client's CPU share is recorded and a measurement above 85 percent of its four CPU budget is marked client limited, which makes its throughput a lower bound.

Repetitions. Four repetitions per workload and engine. The engine order rotates so that each engine takes every position once per workload. Failed, invalid and skipped cases are never retried silently.

Sample. 10 seconds of warmup on the loaded dataset, excluded from the statistics, then one 60 second timed run with four client threads of 8 connections each (32 connections, as in comparison-v1), uniform random keys and pipeline 1 unless the workload names pipeline 16.

Scope. One physical server core with simultaneous multithreading disabled for every engine, four separate physical cores for the load generator and one physical core for the controller, on a rented single-socket bare-metal machine. This is an end to end single core comparison on one machine; it does not measure multicore scaling or maximum capacity.

Seeds. The pinned memtier_benchmark image with its default seed and distinct client seeds, so every engine and repetition sees the same key sequence policy.
